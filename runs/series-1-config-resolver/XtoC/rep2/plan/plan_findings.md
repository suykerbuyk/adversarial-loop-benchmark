minor: Each descriptor gets its own hand-written setter closure that does its own type assertion and builds its own panic message (setter takes *Config, value, layer, key). With N fields that is N copies of the same check-and-panic code, and over time the copies will drift apart (different wording, a forgotten %T, a check that coerces). Write the check once as a generic helper, e.g. func field[T any](ptr func(*Config) *T) setter, which does v.(T), panics with the shared "config: layer %q key %q: want %T, got %T" format, and assigns *ptr(c) = x. Each descriptor entry then becomes one line, such as "MaxRetries": field(func(c *Config) *int { return &c.MaxRetries }). This is still free of reflection and keeps the exact-type guarantee in one place.
minor: Nothing ties the descriptor table to the Config struct. If a maintainer adds a Config field and forgets its descriptor, that field silently becomes impossible to resolve (any layer presenting it panics as an "unknown key", or the key is never considered). If someone renames a key, the old key starts panicking with no compile error. Add a test that uses reflection (in the test only) to check that the set of Config field names exactly matches the descriptor keys, and that each descriptor's setter writes the field with that name. This is cheap, and it is what makes the plan's claim "adding a field = one member + one entry" actually hold.
minor: The plan says neither where the descriptor table lives nor its type. Make it an unexported package-level var that is built once and never mutated (not rebuilt on every Resolve call, and not exported). If it is a map, any code that later needs to enumerate keys, such as listing the legal keys in the unknown-key panic message or writing table-driven tests, must sort them, because map iteration order is random. Either use a slice of {key, set} with a lookup map derived from it, or state that enumeration must be sorted.
nit: The spec only says the four keys are "the only legal keys". It mandates a panic only for wrong-typed values. Panicking on unknown keys is a reasonable, stricter reading that I endorse, but the plan should state in the Resolve doc comment that it is a deliberate programmer-error policy (alongside the wrong-type panic), so a future maintainer doesn't "relax" it into silent ignoring, or tighten it differently, without realizing it was a decision.
nit: The legal LogLevel set and the validation step are hard-coded after application. Keep the accepted levels in one unexported package-level set (e.g. map[string]struct{} or a switch inside a validLogLevel(string) bool function) and call that one function, so adding a level is a one-line change. Do not add a generic per-descriptor validation hook yet: the spec validates only LogLevel, and a speculative hook would just be complexity with no use.
nit: Give the sentinel a package-prefixed message, e.g. errors.New("config: invalid log level"). The wrapped error will then read "config: invalid log level: \"trace\"", which follows Go convention and stays readable when callers wrap it further.
nit: When a layer holds several bad entries, map iteration order decides which one panics, so the panic message is nondeterministic. The plan correctly keeps the tests to one bad entry per invocation. Add one sentence to the plan saying that panic-message assertions must only use substring checks for the layer and key of a single injected fault, so nobody later writes a flaky test.
