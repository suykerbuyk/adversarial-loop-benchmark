# Code Review Findings — XtoC rep3 (round 3)

Verified independently with go1.27.2 in worktree/: `go build ./...`, `go vet ./...`, and `gofmt -l .` (empty) are clean, and `go test -race -count=1 -cover ./...` passes with 100.0% statement coverage. worktree/resolve_public_test.go is byte-identical to instrument/. There is no code_rebuttal.md. All round-2 findings have been addressed in code: there is an `ErrWrongType` sentinel, both panic sentinels are documented as panic-only, the invalid-level error names its layer, the unknown-key tests now check key, layer, sentinel and deterministic choice, the `applyValue` wrapper is gone, the happy path no longer allocates a key slice, a nil `validate` is skipped, and an unexported `resolve([]namedLayer)` engine exists.

I re-probed in scratch copies. A named string type panics with ErrWrongType. When a lower layer has both a wrong-typed value and an unknown key, the lower layer's panic fires first. A lower invalid LogLevel that a higher layer overrides is not validated. All of these match spec.md. In a mutation test, removing `sort.Strings` failed TestUnknownKeyPanicChoiceIsDeterministic in 36 of 40 runs, so that test now has teeth. I found no correctness defect against spec.md.

- [minor] The validation error's layer attribution is hard-coded to LogLevel inside the generic engine (config.go resolve: `if descriptor.key == "LogLevel" { logLevelLayer = layer.name }`, then `fmt.Errorf("%w (from layer %q)", err, logLevelLayer)` for *every* descriptor's validate failure). This silently breaks the extension hook that `field(..., validate)` advertises. Probe: I gave TimeoutSec a `v < 0` validator. `Resolve(nil, nil, {"TimeoutSec": -1}, nil)` returned `negative timeout (from layer "")`. With `{"LogLevel":"info"}` in defaults, it returned `(from layer "defaults")`, although the value came from env. Fix: keep a per-field winning-layer record (e.g. `winners := make([]string, len(fields))` indexed by descriptor, or a map keyed by `descriptor.key`), set it in the apply loop, and use `winners[i]` in the validation loop. The engine then has no field-specific code.
- [nit] The validation loop returns only the first failing validator. That is fine with one validator today, but once fields gain validators, users must fix misconfigurations one at a time. Consider `errors.Join` across all validator errors (each still wraps its sentinel, so `errors.Is` keeps working).
- [nit] Each `validate` closure takes `Config` by value and re-derives the field through `dst(&c)`, which copies the whole struct per validated field. Closing over the resolved pointer or passing `*Config` avoids the copy as the struct grows. The per-field `func(T) error` signature also still cannot express cross-field rules, so a separate `[]func(Config) error` stage would be needed if those arrive.
- [nit] TestWrongTypesPanicEvenWhenOverridden only exercises a wrong type in the *lowest* layer (`defaults`). No test covers a wrong type in `flags`/`env`, or a wrong type alongside a valid higher value for a different key. The behaviour is correct (probed), but a regression that checked types only on the winning or lower layers would go uncaught for the higher layers.
- [nit] The exported `ErrUnsupportedKey`/`ErrWrongType` are now documented as panic-only, which addresses the round-2 concern. They still enlarge the spec's "Input and API (fixed)" surface, and they become a long-term compatibility commitment. Keep them deliberately, or unexport them if recover-and-match is not a supported use.
- [nit] Carried over: go.mod declares module path `config` with `go 1.25`. This is fine for the harness, but a real module path is needed before reuse.

No blocker or major issue remains. All remaining findings are minor or nit, and behaviour against spec.md is correct.
