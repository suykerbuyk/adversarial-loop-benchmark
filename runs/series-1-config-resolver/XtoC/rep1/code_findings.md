# Code findings — adversarial review, round 2 (rep1 worktree)

Checked myself on Go 1.27.2, in a copy of the worktree: `go build ./...`, `go vet ./...` and `gofmt -l` (no output) are clean, and `go test -race -count=1 ./...` passes all 8 public tests and the 6 new tests. Coverage is 96.6%. The worktree's resolve_public_test.go is byte-identical to instrument/resolve_public_test.go. There is still no code_rebuttal.md; the code changes themselves are the response to round 1.
Probes I ran (all match the spec): an invalid lower LogLevel overridden by a valid one gives no error. A named bool, an *int and a nil value each panic with a message naming the layer, key, and expected and actual types. "warning" is rejected and errors.Is is true. 64 concurrent Resolve calls on shared maps show no race.
Mutation tests (all four caught by the suite): MaxRetries writing to TimeoutSec, layer scan order reversed, "trace" allowed, "" removed from the legal levels.
Round-1 status: fixed — the reflection consistency test (the round-1 major), the promised panic, level, no-mutation, zero-Config and Config-returned-with-error tests, the generic fieldOf helper (type written once, so it cannot drift), the doc comment on returning Config with the error, fieldsByKey built once at package level with a duplicate-key panic, and the redundant nil check. Still open — the error-provenance nit and the string panic value nit (both repeated below).

minor: config_test.go TestFieldDescriptorsMatchConfig checks only that each descriptor's key and type match a Config field. It does not check that the descriptor's set closure writes to that field. With two int fields (MaxRetries, TimeoutSec), a copy-paste slip like `fieldOf("TimeoutSec", func(c *Config, v int) { c.MaxRetries = v })` passes this test. My mutation was caught only because TestResolveReturnsResolvedConfigWithInvalidLevel happens to give all four current fields distinct values. A field added later is not covered unless someone also remembers to update that test. That undercuts the plan's claim that adding a field needs only one descriptor entry. Fix: add a generic round-trip test. For each descriptor, build a distinct non-zero value of descriptor.typeOf with reflect, call apply on a zero Config, and check with reflect that the only non-zero field is the one named descriptor.key.
nit: config.go Resolve has the LogLevel check hard-coded as a switch after resolution. The field descriptor has no validate hook. The spec expects more fields over time, so each new validated field means editing Resolve's control flow instead of adding to the descriptor table. Consider an optional `validate func(Config) error` (or a per-field validator built by fieldOf) collected in one loop.
nit: config.go:97 (still open from round 1). The invalid-level error names the bad value but not the layer it came from, e.g. `invalid log level "trace" (from flags layer)`. The winning layer index is already known in the selection loop, so recording it is cheap and helps trace real misconfigurations.
nit: config.go:77,80 (still open from round 1). Panics pass a formatted string, not an error. config_test.go then does an unchecked `recovered.(string)`, so changing to `panic(fmt.Errorf(...))` later would make the test itself panic instead of failing cleanly. Use `fmt.Sprint(recovered)` in the test, or panic with an error value and assert on that.
nit: config_test.go TestResolvePanicsOnInvalidEntries special-cases the "int64 hidden" case by comparing test names (`if tc.name == "int64 hidden"`) to add the masking layer. That breaks quietly if the case is renamed. Add a `mask map[string]any` (or a full `layers [4]map[string]any`) field to the test struct instead.
nit: config_test.go TestResolveEffectiveLogLevels places its three invalid levels at layers 0–2 only, so an invalid level in the flags position is covered only by the public TestInvalidEffectiveLogLevel. Loop every invalid level over all four positions so the table covers the full matrix itself.

Summary: no blocker or major issue remains. The implementation is correct against the spec in every case I tested and probed, all checks are clean, and the round-1 major (the missing reflection consistency test) is fixed. What remains is one minor test gap and some nits on maintainability and tests.
