minor: The reflection test checks field names only, not what each apply function actually does. It confirms each descriptor key matches a Config field name, but each apply closure is still written by hand. A copy-paste slip, such as a new "RetryDelaySec" entry whose closure writes c.TimeoutSec, passes the name check, passes go vet, and leaves the real field at its zero value. This is the most likely mistake when adding a field over the years. Fix: for each descriptor, apply a non-zero sample value of the declared type to an empty Config. Then use reflection to check that the field named by the key now holds that value and every other field is still zero.
minor: The descriptor stores the expected type and the apply function separately (plan line 24), so the two can drift apart. For example, the type says int while the closure asserts int64. Then the closure panics with a raw "interface conversion" message instead of the documented layer/key/expected/actual message, or one of the two checks is dead code. Fix: build each entry with one generic constructor, e.g. field[T bool|int|string](key string, set func(*Config, T)). The constructor derives the type check, the expected-type name in panic messages, and the assignment from the same T. Generics are available (go.mod says go 1.25).
minor: Panics are not deterministic. Phase 1 loops over Go maps, which run in random order. If a layer holds two bad entries (two unknown keys, or an unknown key and a wrong type), the panic names a different entry from run to run. Test item 4 asserts that the panic message names the layer and key. That is only stable if each test case has exactly one bad entry, and the plan doesn't require that. Fix: loop over layers in precedence order and over sorted keys within each layer, so the first reported violation is reproducible. Or state that each panic test has exactly one bad entry.
minor: Panicking on unknown keys goes beyond the spec. Spec lines 17-19 list the legal keys but require a panic only for "a present value of the wrong Go type". Panicking on an illegal key is defensible and consistent with that, and the prior round asked for it, but it is a design choice the spec doesn't require. The plan should say in the Resolve doc comment that any key outside the descriptor table panics, so callers (e.g. a future layer built from decoded JSON with extra keys) know they must filter input first.
minor: Returning the resolved Config together with a non-nil error (plan line 20) breaks the common Go habit of ignoring other results when err != nil. It is allowed by spec line 34, but the plan only says it "deliberately preserves" the data and never says to put this in Resolve's doc comment. Fix: state the contract in the doc comment, e.g. "On ErrInvalidLogLevel the returned Config is fully resolved; all other fields are valid." Test item 6 already pins the behavior.
nit: Phase 1 already proves every present value has the right type, so the type assertions in phase 2 are redundant. If both phases assert separately, they may disagree after a future edit. Either merge into one pass (check every layer's entries, record the winner per field) or have phase 2 reuse phase 1's typed result, so type logic lives in one place.
nit: "provenance can be tracked during selection and included if convenient" (plan line 31) is non-committal. Either decide to put the winning layer's name in the ErrInvalidLogLevel message (cheap, since selection already knows it, and useful for debugging) or drop the sentence. Leaving it optional invites inconsistent messages.
nit: The plan doesn't say what value to panic with. Choose one form (e.g. panic(fmt.Sprintf(...)) or panic of an unexported error type) and say so, so panic tests can use recover() and check the message consistently.
nit: The layer table is internal, but Resolve's four-parameter signature is fixed by the spec. Adding a layer later therefore still changes the public API. Add a short comment saying Resolve is a thin adapter over an internal resolve([]layer) and that new layers go in that table first. This makes the extension path the plan claims explicit.
No blocker or major issue remains. All nine prior findings are fixed in the revised plan, which I re-checked against spec lines 16-19, 37-49 and 55 and the eight public tests. The remaining items are minor hardening and documentation.
