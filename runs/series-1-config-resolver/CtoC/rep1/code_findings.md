minor: The table-sync guard does not check what its comment says. In resolve_internal_test.go:274-282 the comment says applying a zero value "must leave the field at that value", but the test only checks that `apply` does not panic. It never reads the field back and never checks which field changed. So a binding that compiles but points at the wrong field of the same type gets through. I checked this with mutations. Changing the binding to `bind("MaxRetries", ... &c.TimeoutSec)` passes TestFieldsTableInSync; only the hand-kept `fieldCases` matrix catches it. Adding a new field `Port int` bound to `&c.TimeoutSec` passes the whole suite (`ok config`), and `Resolve({"Port":5})` sets TimeoutSec=5 and leaves Port=0. The plan review raised this exact issue (plan_findings #2) and it was not fixed. Fix: for each `fields` entry, apply a non-zero value of the field's reflect type to a zero Config and check that only the struct field named `f.name` changed. Alternatively, build `fieldCases` from reflection so new fields get matrix coverage automatically.
minor: A test fixes behaviour the spec leaves open, against the plan review's advice. TestInvalidLogLevels (resolve_internal_test.go:152) requires a zero Config on error. The spec says Resolve "returns the effective Config and an error". Returning `Config{}` is a reasonable Go convention and the `Resolve` doc comment now documents it, which is fine. But a test that enforces it turns an interpretation into a regression contract, and plan_findings #1 said explicitly not to add one. Remove that check, or label the test as covering a deliberate design choice and not a spec requirement.
minor: Panic and error messages do not say which layer is at fault. `resolve` is variadic and drops the layer identity, so a wrong-type panic ("key \"MaxRetries\": value \"3\" has type string"), an unknown-key panic, and the ErrInvalidLogLevel error never say whether defaults, file, env, or flags supplied the value. That is the most useful piece of information when debugging layered config, and it matters more as layers are added. Pass layer names alongside the maps (e.g. a small `[]struct{name string; m map[string]any}`) and put the name in panic and error messages. Keep the `%w` wrapping so `errors.Is` still works.
minor: Validation is still separate from the field table that is described as the single source of truth. `validLogLevels` and `validate` in validate.go are hard-coded to LogLevel. Adding a validated field means editing two unrelated places, and no test connects a validator to its descriptor. This is plan_findings #4, not fixed. Consider an optional per-field validator in `field`/`bind` that runs once on the effective value after all layers are applied.
nit: Panicking on an unknown key (fields.go:48-66) goes beyond the spec, which only requires a panic for a wrong-type value. It is defensible because the spec lists "the only legal keys", and the `Resolve` doc comment discloses it. Still, callers who build layers from user input should know a typo in a key crashes the process. Consider stating in the package doc that callers must normalise keys first.
nit: The wrong-type panic formats the caller's value with `%#v` (fields.go:21). A large value (for example a big slice or map placed under a scalar key) is dumped into the panic message in full. `%T` plus the key identifies the problem; truncate the value or drop it.
nit: `validLogLevels` is a mutable package-level map. A read-only switch or a `slices.Contains` over a fixed array would rule out an accidental write from elsewhere in the package. This is purely defensive; lookup performance is not affected.
nit: Panics carry a plain `string`. Panicking with an `error` value (for example `fmt.Errorf` wrapping an unexported `errProgrammer` sentinel) would let recover-based test harnesses or top-level crash handlers classify the panic. This is cosmetic.
nit: The exported `Resolve` signature is fixed at four positional parameters, so adding a fifth layer is a breaking API change however general `resolve(...)` is inside. The "more layers" goal in the spec is only partly met. Document this, or plan an additive `ResolveLayers(...)` entry point later. (This is plan_findings nit #1; still applies.)
Verified independently: `go build`, `go vet`, `gofmt -l` are clean, and `go test -race -count=1 ./...` passes with 100% statement coverage (go1.27.2). worktree/resolve_public_test.go is byte-identical to instrument/resolve_public_test.go. From source, I re-derived each spec rule. Presence is decided by comma-ok, not by zero value, so present false/0/"" override. Absent fields show through, nil layers present nothing, and fields no layer presents keep Go zero values. Only the effective LogLevel is validated, "" is legal, and the match is case-sensitive. Errors wrap ErrInvalidLogLevel with `%w`. A wrong-type value panics in every layer, including overridden layers, and for explicit nil and named types. Inputs are only read, and package state is read-only, so concurrent calls are safe. checkKeys' count shortcut is correct because map keys are unique. I found no correctness, race, or resource defects.
