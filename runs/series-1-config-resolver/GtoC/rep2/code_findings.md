# Code findings — round 1 (adversarial review of worktree)

Verification performed independently: `go build ./...`, `go vet ./...`, `gofmt -l .` all clean; `go test -count=1 -race -cover ./...` passes (89.7% coverage; uncovered lines are only the unreachable defensive `default:` panic arms). The worktree's `resolve_public_test.go` is byte-identical to `instrument/resolve_public_test.go`. No `code_rebuttal.md` exists (first code round). golangci-lint could not be run (installed binary cannot read Go 1.27 export data; tool issue, not a code issue). Each spec rule was re-derived against `resolve.go`: the low-to-high full scan writes a field only when its key is present (so false/0/"" override and absent keys show through), a zero `Config` start gives the Go zero for fields no layer presents, `validate` runs once on the merged value (so overridden illegal levels are never checked and `""` is legal), and wrong dynamic types (including nil) panic via `apply`. All eight public cases hold.

minor: Adding a field takes three hand edits (struct field, `fieldCatalog` row, `apply` write arm), and nothing at test time checks the third. Verified by mutation: adding `DryRun bool` to `Config` plus `{key: "DryRun", kind: kindBool}` to the catalog with no `apply` arm passes the whole suite (`ok config`). The gap shows only at runtime, when a caller presents the key: `panic: config: key "DryRun" has no bool write arm`. Round-2 plan finding 2 raised exactly this, and the code did not address it. Fix: in `TestCatalogCoversExportedConfigFields`, call `apply` for each catalog row with a non-zero sample of its kind and use reflection to check that the named field changed.
minor: Panic messages name the key and the dynamic type but not the layer (resolve.go:85, 100, 111, 124). In a package that merges several sources, `config: key "MaxRetries": got string, want int` doesn't say whether the bad value came from defaults, file, env, or flags. This gets worse as layers are added. Round-2 plan finding 3 raised this, and the code did not address it. Fix: pass a layer index or name into the scan, put it in the panic text, and keep the tests asserting only that a panic happened.
nit: `apply` dispatches twice, on `spec.kind` and then on `spec.key`. Since the key alone decides the target field, `kind` duplicates information that each arm already encodes. A single `switch key { case "Verbose": dst.Verbose = must[bool](key, v) ... }` with a generic `must[T]` helper would put key, type, and write in one place and remove the impossible `no X write arm` branches, which are uncovered code (the only reason coverage is below 100%).
nit: `TestEachLegalLogLevelFromFlags` loops over the implementation's own `legalLogLevels`, so it is tautological. It can't detect an illegal value added to the set (e.g. `"Debug"` or `"trace "`) or a legal one dropped. Today a dropped or misspelled `"error"` is caught, but only incidentally by `TestNegativeIntsAccepted`; I verified this by mutation. The other four legal levels are covered only incidentally by public tests. Fix: write the spec's five literals in the test.
nit: `TestErrInvalidLogLevelStable` has a dead assertion. `if ErrInvalidLogLevel != sentinel` compares a variable with a copy of itself taken a few lines earlier, so it can never fail. `errors.Is(err, sentinel) || errors.Is(err, ErrInvalidLogLevel)` tests the same thing twice. Round-2 plan finding 7 asked for this to be dropped. The useful checks (non-nil, and wrapped rather than bare) are present; delete the tautological lines.
nit: `kindBool` is `iota` (0), so a catalog row that leaves out `kind` silently becomes bool. The reflection test currently catches this (verified by mutation: a missing kind on `TimeoutSec` fails the suite), so the risk is low. Still, starting the enum at `kindInvalid` would make `apply`'s `unknown kind` arm live code instead of dead code.
nit: When one layer has more than one programmer error (e.g. an unknown key and a wrong type), which panic fires depends on Go's randomized map iteration order, so the panic message is nondeterministic from run to run. It always panics, so correctness is fine. Iterating `fieldCatalog` order and then checking leftover keys would make diagnostics reproducible.
nit: The `if layer == nil { continue }` check in `resolve` is redundant, because ranging over a nil map is a no-op in Go. It is harmless, but it suggests nil needs special handling when it doesn't.
nit: The `Config` doc comment says "Field order and names are fixed; tests compare with ==." That puts a test-suite detail into the exported API doc. Comparability matters to callers, but the reason belongs in the tests.
nit: Unknown keys panic, which goes beyond the spec's explicit panic rule (wrong Go type only). This is documented as a design decision in doc.go and is a reasonable reading of "the only legal keys are…". I note it only as a behavior a caller might not expect; no change is required.

No blocker or major issue remains. The implementation meets every rule in the spec and passes the public and additional tests under -race. The remaining items are test-strength, diagnosability, and maintainability concerns.
