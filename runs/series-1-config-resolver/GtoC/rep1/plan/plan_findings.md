minor: Field descriptors encode the type twice: a `kind` enum checked by `assertType`, and a `set func(*Config, any)` that must type-assert again ("type already checked"). The two can drift apart (kind says int, setter asserts string). The plan also says adding a field is "one registration", but that is only true for bool/int/string. A new type such as time.Duration or float64 means editing the fieldKind enum, the assertType switch, and the setter. Fix: drop `kind`. Use one generic constructor, e.g. `func field[T any](key string, dst func(*Config) *T) fieldDesc`, whose `apply(*Config, any)` does `v, ok := raw.(T)` and panics with key and %T when !ok. Each field is then one line for any type, and one code path owns the type check and the panic text.
minor: The "Present vs absent" section offers two loop shapes: `v, ok := layer[desc.key]` (loop over descriptors, look up each key) OR range the map and match descriptors. These behave differently. Looping over descriptors silently ignores unknown keys, which breaks the plan's own panic contract and its additional test 9. Pick one shape. Recommended: loop over the map and look up each key in a descriptor index, so unknown keys are always found.
minor: Panics are not deterministic when one layer has more than one bad entry. Go map iteration order is random, so which key panics (and the panic message) changes from run to run, which makes failures hard to reproduce. Either state that only "panics" is promised, not which key, or check keys in sorted or descriptor order before applying.
minor: Validation is placed inconsistently. LogLevel is checked by a hard-coded switch in Resolve, yet the extensibility section says future per-field validation is "a method on fieldDesc invoked once after merge". Put the LogLevel check on its descriptor now (e.g. an optional `validate func(Config) error` run once over all descriptors after the merge). Then the pattern exists and is tested from day one, instead of a special case the next maintainer has to generalise.
minor: Adding a layer means changing Resolve's exported signature, which breaks every caller; the plan's extensibility story is "insert a parameter". Make Resolve a thin wrapper over an unexported `resolve(layers ...map[string]any)` (lowest precedence first). Extra tests can then check N-layer precedence directly, and a future public variadic or named-layer API costs nothing.
minor: Panicking on unknown keys is presented as part of the spec's panic contract, but the spec only says wrong-typed values "must panic". It only lists the legal keys and never says what happens to other keys. Panicking is a defensible reading (an illegal key is a programmer error), but the code comment and package docs should call it a design decision, not a spec requirement.
minor: Missing tests: (a) a present key with an untyped nil value (`{"LogLevel": nil}`), which is present and wrongly typed, so it must panic, not count as absent; (b) a named type (`type lvl string; {"LogLevel": lvl("info")}`), which is the wrong Go type under the exact-type rule and must panic; (c) the input maps are unchanged after Resolve. The plan states (b) and (c) as behaviour but nothing locks them in.
nit: Error text will repeat itself. The wrap is `"config: invalid log level %q: %w"` and the sentinel text is meant to "document the legal set" with a similar prefix, giving e.g. `config: invalid log level "trace": config: invalid log level (want debug|info|warn|error|"")`. Keep the sentinel short (`errors.New("config: invalid log level")`) and put the value and the legal set in the wrap.
nit: Returning the merged Config together with a non-nil error is allowed but less common Go practice than returning `Config{}` on error. Either is fine; write the choice in Resolve's doc comment so callers do not come to depend on whichever happens to be implemented.
nit: The descriptor list is a mutable package-level slice that any file in the package can change. Linear lookup is fine at 4 entries, but a lookup map built once from the slice (in a var initializer or init) gives O(1) lookup and somewhere to catch duplicate keys at startup as the field list grows.
nit: The doc comment should say Resolve is pure and safe for concurrent use (no shared mutable state, inputs not retained). Callers in a long-lived codebase will rely on this.
No blocker or major issues remain: re-deriving each rule from the spec and the eight public tests, the plan's algorithm (start from Config{}, apply layers from lowest to highest precedence, presence = map membership, panic on wrong type on any layer, validate only the effective LogLevel against {debug, info, warn, error, ""}, wrap the sentinel with %w) meets every stated rule and passes every public test.
