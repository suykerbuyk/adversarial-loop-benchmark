minor: The implementation addresses none of the 11 approved plan findings (plan/plan_findings.md), and the implementor wrote neither a rebuttal nor a code_rebuttal.md. Each plan finding below that is still present in config.go is re-raised with fresh evidence. They should be fixed or rebutted explicitly rather than silently dropped.
minor: config.go:30-42,53-70 states each field's type twice. The `kind` enum is checked in assertType, and the `set` closure does its own unchecked `v.(T)` assertion. I simulated drift (setting fields[1].kind=kindString for MaxRetries) and passing "x" then panics with a raw runtime error, "interface conversion: interface {} is string, not int", instead of the package's documented "config: key ...: want int" message. Adding a field of a new type (time.Duration, float64, []string) means editing the enum, the assertType switch and a setter, so "one descriptor and one Config field" (comment at line 36) is only true for bool/int/string. Fix: replace kind+set with a generic constructor `func field[T any](key string, dst func(*Config) *T) fieldDesc`. Its apply method should do `v, ok := raw.(T)` and panic with the key and %T, so the type check and the panic text live in one code path for any type.
minor: config.go:99 hard-codes LogLevel validation in Resolve, outside the descriptor table. The plan's own extensibility section says per-field validation runs from the descriptor, once after merge, on the effective value. The next validated field will need a second special case in Resolve, or someone will have to generalise this one. Fix: add an optional `validate func(Config) error` (or a per-value validator) to fieldDesc and loop over the descriptors after the merge. LogLevel would be its first user, which gives the pattern test coverage from day one.
minor: config.go:93-97 makes panics non-deterministic when a layer has more than one bad entry. Go map order is random. In 200 runs with one layer holding 5 bad keys, the panic message differed across all 5 variants (Verbose 95, TimeoutSec 28, Zzz 29, LogLevel 27, MaxRetries 21). That makes failures hard to reproduce. Fix: check each layer's keys in a fixed order before applying them (descriptor order, plus sorted unknown keys), or document that only "panics" is promised, not which key.
minor: config.go:84-86 and the package docs present the unknown-key panic as part of the spec contract ("A present key outside the legal set ... is a programmer error and panics"). The spec only requires a panic for a wrong Go type. For other keys it lists the legal set and says nothing more. Panicking is a defensible reading, but the doc comment should label it a deliberate design choice so a future maintainer does not mistake it for a spec requirement.
minor: Resolve returns the merged Config together with a non-nil error. I confirmed `{false 3 trace 0}` comes back alongside ErrInvalidLogLevel. The doc comment (config.go:81-85) never says this, so callers may start relying on the partially valid struct, or assume Config{} on error. Pick one behaviour and document it. Idiomatic Go would return Config{} with the error.
minor: resolve_test.go is missing tests for three behaviours that the plan states and that I verified only by probing. (a) A present untyped nil `{"LogLevel": nil}` must panic, not count as absent; it currently panics with "want string, got <nil>". (b) A named type `lvl("info")` must panic under the exact-type rule; it currently does. (c) The input maps must not be mutated; currently they are not. Nothing in the suite would catch a regression to "nil means absent", a reflect-based Kind() check that accepts named types, or a map mutation.
minor: The four-layer list is built inside the exported Resolve (config.go:88). The only way to add a layer is to change the public signature, and no test can check N-layer precedence directly. Fix: make Resolve a one-line wrapper over an unexported `resolve(layers ...map[string]any)` (lowest precedence first) and test it with 1..N layers. A future variadic or named-layer public API then needs no changes to the merge logic.
nit: config.go:12+77 make the error text repeat itself. The actual Error() string is: `config: invalid log level "trace": config: invalid log level; legal values are debug, info, warn, error, and empty`. Fix: shorten the sentinel to `errors.New("config: invalid log level")` and put the value and the legal set in the wrapping message only.
nit: config.go:99-102 `if err := validateLogLevel(...); err != nil { return cfg, err }; return cfg, nil` is equivalent to `return cfg, validateLogLevel(cfg.LogLevel)`. The extra branch adds nothing.
nit: config.go:67-68 is dead code: the `default` branch of assertType is unreachable with the current descriptors and is the only uncovered statement (coverage 96.8%). It exists only because of the kind/set duplication above and goes away with the generic-descriptor fix.
nit: config.go:37,44-51 keeps `fields` as a mutable package-level slice searched linearly, with no check for duplicate keys. A map built once in a var initializer would give O(1) lookup and could panic on a duplicate key at init, a real hazard as the field list grows.
nit: The Resolve doc comment does not say the function is pure and safe for concurrent use. I verified both: 50 concurrent goroutines sharing the same input maps pass under -race, and there is no shared mutable state. Long-lived callers will depend on this guarantee, so it should be written down.
Verification: go1.27.2 (go.mod declares 1.25); `go build ./...`, `go vet ./...` and `gofmt -l .` are clean; `go test -race -count=1 -cover ./...` passes at 96.8% coverage. The worktree resolve_public_test.go is byte-identical to instrument/resolve_public_test.go. I re-derived the rules from source: start from Config{}; apply layers from lowest to highest precedence; presence means map membership, so false, 0 and "" override; absent keys show through; nil layers are skipped; a wrong type or unknown key panics on any layer, including overridden ones; only the effective LogLevel is validated against {debug, info, warn, error, ""}, with the sentinel wrapped via %w; case variants such as "INFO" are rejected; other fields are not validated; inputs are not mutated; there is no data race.
