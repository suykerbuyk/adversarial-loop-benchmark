minor: §5.6(b) says the read-through test is built so that "only the sub-slice bound can be what rejects the stream", but that is not true as specified. The 9 bytes `filler(5)|innerCRC(4)` also sit after the outer frame in the *top-level* stream. Take a buggy decoder that reads the over-long inner frame through the Batch boundary and skips the off==len check: it then resumes at the top level and parses `filler` as a frame header. If the filler's first 4 bytes encode a len L with L+8 > 9 (for example L=2) and L <= 16 MiB, that decoder reports "truncated frame", so it passes both the `ErrCorrupt` and the `Contains("truncated")` assertions. The plan leaves the filler bytes unspecified. Fix: pin the filler (for example the first 4 bytes = 0xFFFFFFFF, so a top-level read gives "exceeds limit", not "truncated"), and assert the batch context, not just the word. For example, require "batch:" to appear before "truncated" (the correct decoder yields `... frame 0 at offset 0: batch: frame 0 at offset 0: truncated frame`, which I checked with a prototype of the plan), or check an unexported sentinel/type with errors.Is/As.
minor: The plan's error-layering rule [F2] has every inner layer wrap with `%w`, but `Decode` then calls `corrupt("%v", err)`, which flattens the chain to text. So the inner `%w` chain is dead weight: no caller and no test can `errors.As` or `errors.Is` anything below ErrCorrupt, and the §5.6(b) and §5.1 tests have to fall back on substring matching (fragile over years, since any reword breaks them). Either make the chain real (`fmt.Errorf("%w: %w", ErrCorrupt, err)`, plus unexported sentinels such as errTruncated and errTooDeep that the internal tests match with errors.Is), or use `%v` throughout and say so. Pick one and document it.
nit: `kindAllowed` returns false both for an unknown tag (99) and for tag 3 in a v1 stream, and `decodeFrame` reports both as "record type %d not allowed in version %d". An unknown tag in a v2 stream therefore gets the misleading text "record type 99 not allowed in version 2", and the "defensive" `default: unknown record type` arm in `decodePayload` is unreachable by construction, which a coverage report will flag forever. Distinguish the two: check known kinds first and report "unknown record type", then check the version and report "not allowed in version".
nit: Frame offsets in Decode errors become relative to the enclosing region (§2.3), so top-level offsets are now 1 less than v1's, which were absolute offsets in `b`, and nested offsets cannot be mapped to a byte position in the input. For a WAL, the absolute offset of the first bad frame is the operationally useful number (it is the truncation point for recovery). Pass a `base` offset down so every reported offset is absolute in `b`, or document that offsets are region-relative.
nit: §2.3 `readFrame` returns a value named `payload` that is actually type+payload (the body), and callers must remember `payload[1:]`. Name it `body`, or return the payload with the tag already stripped (`kind` is returned separately anyway), so a future caller cannot pass the tag byte as payload by mistake.
nit: The depth detail text hard-codes "exceeds depth 8" in two places (encoder and decoder) while the check uses `maxDepth`. Format the text from the constant (`"batch nesting exceeds depth %d", maxDepth`) so a future cap change cannot leave stale messages behind, and so encoder and decoder share one message source.
nit: §2.1 lists the doc comments to update (package, Record, Encode, Decode) but leaves out `ErrCorrupt`, whose v1 doc says "ErrCorrupt is wrapped by every error returned from Decode". After [F1], Encode's depth error also wraps it. Update the `ErrCorrupt` doc so the exported contract appears in one place, not only in Encode's comment.
nit: §5.12 tests the Batch frame cap at exactly 16 MiB (accepted) and at "two 9 MiB Puts" (far over), but not at the off-by-one boundary 16 MiB+1. The running-sum check `1+payloadLen > maxFrameLen` is exactly the kind of comparison that drifts to `>=` or loses the `1+`. Add an exact cap+1 Batch case on the encoder side, and on the decoder side a hand-built Batch frame with an inner frame at len = 16 MiB+1.
nit: §5.9 runs `testing.Benchmark` inside unit tests. Each call takes about 1 s of benchtime (I measured 1.1 s, and about 1.3 s under -race), which adds about 2-3 s to every `go test`, including the test run before each fuzz session. Also, if the regression it guards against returns, the `n=0xFFFFFFFF` case tries a ~64 GiB `make` and is more likely to OOM-kill the test binary than to fail cleanly. Run the `1<<24` case first, or measure one call with `runtime.ReadMemStats` TotalAlloc deltas instead of a full benchmark.
nit: §1 keeps v1's `math.MaxInt` guard and its comment "on 64-bit the input cannot exist" unchanged. That comment was already false for shared Put values. With Batch it is cheaper still to build an input whose expanded size is enormous: a few KB of shared `Records` slices can fan out to terabytes of frames, which pass every per-frame cap and are then sized by an O(expanded-tree) walk before `make` aborts the process. This is not a spec violation (no total-stream cap is specified), but the comment should be corrected, and a doc sentence should say that Encode's cost is proportional to the expanded output, not to the in-memory input.
