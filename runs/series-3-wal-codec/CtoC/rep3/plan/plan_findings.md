minor: §4 step 4 says the capacity hint `min(n, len(region)/13)` means a hostile count "cannot trigger a huge allocation". That only holds at one level. Nested regions overlap and every level's hint is allocated before any child fails, so a chain of 8 Batches each claiming n=0xFFFFFFFF around one ~16 MiB child holds about 165 MB live for a 16.0 MB input (9.8x, measured). v1's decoder had no such amplification. Test 6.6 only covers an empty region, so it cannot catch this. Fix: either (a) pre-scan the region's frame headers (a cheap length walk, no CRC) to get the real frame count and reject fewer/more/trailing before allocating, then allocate exactly; or (b) cap the hint at a small constant and let append grow. Add a nested hostile-count allocation test.
minor: the two-pass encoder keeps two independent sources of truth for the wire layout: `frameLen` (pass 1) and `appendFrame`/`appendField` (pass 2), plus a third type switch in `decodeRecord`. The 16 MiB cap is enforced only on pass 1's arithmetic, while pass 2 backpatches `len` from the bytes actually written. If the two ever drift (e.g. a future record kind or field change), the encoder silently emits a frame whose real `len` exceeds the cap or differs from what was validated. That breaks "the encoder will not emit a stream it would itself reject", and only the cap==len test (6.12) would notice. Fix: add a cheap invariant in pass 2. `finishFrame` should check that the backpatched len equals the pass-1 value (or is <= maxFrameLen), and Encode should check `len(out) == total` at the end, returning an internal error rather than emitting bytes.
