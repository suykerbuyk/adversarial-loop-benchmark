minor: Allocation amplification on hostile nested input (§2.4 decodeBatch step 3). Each nesting level preallocates min(n, remaining/9) interface slots *before* it reads its first inner frame, and those reservations add up across up to 8 levels. A prototype that follows the plan exactly allocated 213 MiB to reject a 15 MiB v2 stream: 8 nested Batches, each claiming n=0xFFFFFFFF, around junk. That is about 14x amplification before ErrCorrupt. The plan's safety claim ("never make from the untrusted n") holds per level but not overall. Fix: don't preallocate from n. Grow `recs` with append (or preallocate only min(n, small constant such as 64)) and convert nil to []Record{} at the end. This costs nothing on valid input.
minor: An inner oversize `len` can be rejected *after* an allocation, which conflicts with the v1 rule ("rejected before any allocation"). The amendment extends that rule to "every frame at every depth". decodeBatch runs its `make` before readFrame checks the first inner `len`. The prototype gave 0 allocs when the Batch payload after `n` is under 9 bytes, but 1 alloc when filler bytes follow the bogus inner header (n=2, len=16MiB+1, 9 more bytes). Impl test 9 therefore passes or fails depending on how the fixture is shaped, and a grader-built fixture could expose it. Fix: same as above (append from nil, so the first allocation happens only after a frame has fully validated). Also make test 9 include trailing filler, so it really tests "zero allocations before the cap check".
minor: The write pass does more and more redundant sizing work as nesting deepens. appendFrame "recompute[s] n via payloadLen (or carry it)", and payloadLen on a Batch walks its whole subtree. So every node is re-sized once for each ancestor. For a 9-node chain the prototype made 54 payloadLen calls where 9 would do: about depth^2/2, plus the sizing pass. It is bounded (depth ≤ 8), but it is wasteful, and "or carry it" leaves the design undecided. Fix: pick one. Either reserve 4 bytes for `len`, write type+payload, then back-patch with binary.BigEndian.PutUint32(dst[lenPos:], uint32(len(dst)-start)), or carry the sizes. Back-patching also removes any chance that the sizing logic and the writing logic drift apart.
nit: `minFrameSize = 9` is described as "the smallest possible frame", but the smallest frame that can *decode* is 13 bytes (empty-key Delete or empty Batch: 4+1+4+4). 9 is a safe but loose bound. Either rename it (e.g. `minFrameHeader`) or use 13 with a comment. If the finding above is fixed, the constant is not needed at all.
nit: The version-to-kind policy is hard-coded as `allowBatch bool`, threaded through decodeStream and decodeRecord. A v3 that adds another kind would need another bool or a rewrite. A small per-version table of allowed kinds (or passing the version itself) would make the version rule live in one place.
nit: Step 0 says to exclude the v2 file with "`go test -run . ./...` on a scratch copy". `-run .` excludes nothing; only leaving the v2 test file out of the scratch copy works. Say so explicitly, so nobody edits or renames the public file in the worktree.
nit: The structure-corruption table (impl test 7) works only one Batch level deep. The rule "never a read into the next outer frame" matters most when a depth-2 inner `len` overruns its Batch but would fit inside the depth-1 parent. Add at least one depth ≥2 overrun case and one depth ≥2 count-mismatch case.
nit: §2.1 only updates the doc comments of the package and Encode. The `Record` interface doc ("a single log entry") and the Batch doc should mention that Batch may nest (≤ 8 levels) and that a nil `Records` decodes back as an empty non-nil slice, since that asymmetry is user-visible.
No blocker or major issue remains. I checked these from the amendment and the public tests, not from the plan's own description, and confirmed them with a throwaway prototype written to the plan's design. The prototype passed both public suites and go vet (amd64 and 386). Depth convention (top-level 0, sub-stream > 8 rejected) matches public test 7: 8 nested Batches round-trip; 9, including 9 with an empty innermost Batch, are rejected by both Encode and Decode. Self-referential (cyclic) Batches, as a value and through *Batch, return an Encode error rather than overflowing the stack. The v1 fixture's decode, crc flip and truncation all behave as the tests expect. A 20 s fuzz (8.1M execs) found no input where Decode returns anything but bare ErrCorrupt on failure, and every accepted input re-encodes to the same bytes after the version byte.
