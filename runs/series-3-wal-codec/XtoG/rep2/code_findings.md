minor: `encodeRecords` duplicates the entire `Batch` arm for `*Batch` (`walcodec.go` lines 87-129) instead of one payload builder plus a nil-pointer check. The two copies must stay identical for the depth cap (`depth+1 > 8`), the `uint32` count limit, and the enclosing 16 MiB check. A later kind or a fix applied to only one arm will encode a value and its pointer differently, which is how a Batch frame skips a cap the other arm still enforces. Collapse to one function that builds a Batch payload from `[]Record`, and keep pointer handling as the nil check already used for `*Put` and `*Delete`.
minor: A Batch that cannot fit its children is rejected only after those children are fully encoded. The size test is inside the append loop (`uint64(len(payload))+uint64(len(child))+1 > maxFrameLen`) after `encodeRecords` has already returned every child frame. I measured `Encode` of `Batch{Delete{Key: 16MiB-5 bytes}}`: the child is a legal frame, the parent is not, and the call correctly returns `errEncode` with a nil buffer, but `TotalAlloc` rose by about 50 MiB (the child frame plus copies) before the reject. The amendment requires the encoder not to emit a stream it would reject; it does not require spending a full child allocation to discover that. Sum child frame lengths, or reject when the running total would pass `16<<20`, before building the child bodies.
nit: `Encode` copies every frame into a `[][]byte` and then appends those frames onto the version byte (`walcodec.go` lines 39-48 and 145). Nested Batches do that again, so a deep record is copied once per enclosing level plus the final stream. A single `[]byte` writer passed down the recursion avoids the intermediate slices and the `for _, f := range frames { out = append(out, f...) }` copy.
nit: `validPutSize` allows a key or value up to `^uint32(0)` and then requires `len(key)+len(value)+9 <= 16<<20`. On this platform `len` cannot exceed the frame cap, so the `MaxUint32` clauses never fire, and a reader can think a 4 GiB key is representable until the frame cap. Delete checks only `len(key)+5 > maxFrameLen`. One helper for "type byte + length prefixes + fields fits in `maxFrameLen`" would make the two payload kinds share the same bound.
No blocker or major issue remains. `go test`, `go vet`, and `go build` pass in `worktree`. Decode accepts versions 1 and 2, rejects 0 and 3 before frames, rejects Kind 3 in a version-1 stream, accepts 8 nested Batches, and rejects a 9th on both Encode and Decode. Inner `len` past the enclosing Batch payload, hostile `count` (`0xffffffff` and count above `(len-4)/9`), trailing bytes, inner CRC/tag/zero-length/oversize failures, and the exact 16 MiB frame boundary all return `ErrCorrupt` with no panic. The fixed v1 fixture decodes to Put `alpha`/`one` then Delete `beta`.
