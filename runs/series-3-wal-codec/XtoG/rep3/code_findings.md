minor: Encode rejects an over-cap Batch only after the children are fully encoded. In encodeFrame the Batch arm calls encodeFrame on each child, then checks uint64(len(p))+uint64(len(f)) > maxFrame (walcodec.go lines 77-85). A Delete whose key is 16MiB-5 bytes is a legal frame, but wrapping it in a Batch exceeds the 16 MiB type-plus-payload cap. That call returns (nil, ErrType), which is the right result, and TotalAlloc still rose by about 50 MiB building the child frame and the copies around it. The cap is the same at every depth, so a nest of near-cap frames pays that cost at each level before the outer frame is rejected. Sum the child frame sizes, or stop when the running total would pass 16<<20, before retaining child bodies.
nit: decodeRecord parses a Batch by slicing one frame and calling decodeStream, then requiring len(parsed)==1 (walcodec.go lines 176-190). decodeStream is a multi-frame loop with its own leftover-byte check, so this path re-walks a buffer that the caller already bounded and maps every inner failure, including a multi-record result that this slice cannot produce, onto a bare ErrCorrupt. A single-frame reader shared by the top-level loop and the Batch loop would keep the length, CRC, and kind checks in one place.
nit: encodeFrame allocates a fresh payload, a fresh type-plus-payload body, and a fresh frame for every record (walcodec.go lines 53-99), and the Batch arm appends those frames into yet another slice. A nested record is copied once per enclosing level plus the final stream. One buffer passed down the recursion would drop the intermediate copies.

Inner len past the enclosing payload, a hostile count (0xffffffff and count above remaining/9), trailing bytes, fewer frames than n, inner CRC/unknown-type/zero-len/oversize failures, and a following sibling frame all return ErrCorrupt with a nil record slice and no panic.
