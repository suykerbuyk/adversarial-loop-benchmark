minor: The encoder's over-depth error is defined only in plan_rebuttal.md (#4: "wraps ErrCorrupt, distinguish via message"), not in plan.md. Change 2 of plan.md lists only ErrUnsupportedRecord and ErrRecordTooLarge as Encode errors, so the authoritative plan leaves depth overflow unspecified. The rebuttal's choice is also weak: ErrCorrupt is documented (v1 spec and source) as "malformed or unsupported encoded stream", a decode-side condition, while an over-deep Encode input is an invalid *input record*, the same class as ErrUnsupportedRecord. Telling callers to parse the message string is a fragile API contract that will last for years. Fix: put the decision in plan.md and prefer wrapping ErrUnsupportedRecord (whose comment is being rewritten anyway) with a depth message, or document clearly why ErrCorrupt was chosen. Either way, add an `errors.Is` assertion to the planned 9-level Encode-rejection test.
minor: Change 7 and rebuttal #7 claim the design "avoids separate size and payload switches", but the design described still has two independent per-kind switches: `frameBodySize` (size, kind, and depth authority) and the per-kind emitter (payload bytes), plus the decode dispatch. If they drift, for example a future field added to the emitter but not the sizer, Encode silently writes a `len` that disagrees with the bytes and produces a stream its own decoder rejects, which violates "the encoder will not emit a stream it would itself reject". Fix: write `len` from the bytes actually emitted (reserve 4 bytes, append, backpatch), and use the pre-pass only for cap and depth validation. Alternatively, assert after each frame that emitted length == computed size, and return an internal error if not.
minor: The plan commits to many supplemental tests but never says where they live. It also doesn't say the shipped public files (walcodec_public_test.go, walcodec_v2_public_test.go) stay byte-for-byte unmodified, even though they are acceptance artifacts. Both public files share package walcodec and already claim `beU32`, `mkFrame`, `recEq`, `recsEq`, `be2`, `mkFrame2`, `putPL2`, `batchPL2`, `recEq2`, `recsEq2`, `v1Fixture`, and `v1FixtureRecords`. A third file that redeclares any of these fails compilation of the whole package, including acceptance. Fix: name a separate file (e.g. walcodec_v2_extra_test.go), reuse the existing helpers instead of redeclaring them, and state that the public files are not edited.
minor: The verification plan runs only `go test`. The deliverables carried over from v1 also require `go build` and a clean `go vet` (`go test` runs only a subset of vet analyzers). Add `go build ./... && go vet ./... && gofmt -l .` (expect no output from gofmt) to the verification step.
nit: The error contract between payload decoders becomes inconsistent. v1's `decodePutPayload`/`decodeDeletePayload` return plain errors that `Decode` wraps once via `corrupt(pos, "%v", err)`. The planned Batch decoder recurses into the shared frame parser, which already returns ErrCorrupt-wrapped errors with absolute offsets. Pushed through the same `corrupt(pos, "%v", err)` path, those errors produce doubled messages ("walcodec: corrupt stream at byte 7: walcodec: corrupt stream at byte 19: ...") and hide the precise inner offset that change 4 promises. The plan should say nested-parser errors are returned unchanged, and give the per-kind payload decoders one uniform signature (e.g. payload, base offset, depth).
nit: Nested Encode error locations are unspecified. v1 reports "record %d" using only the top-level index. For an unsupported or over-deep record inside a Batch, the plan should report a path (e.g. "record 3.2.5") so the failing element can be found.
nit: The version-specific allowed-type set (v1: {1,2}; v2: {1,2,3}) should live in one place, a function or table keyed by version and passed to the shared parser. Otherwise the type-3 rule ends up as an ad-hoc `if version == 1` inside the dispatch switch, and a future v3 has to update scattered conditionals. The plan states the rule but not where it lives.
nit: The pre-encode depth check also guards against a self-referential input: Go allows `b := Batch{Records: make([]Record, 1)}; b.Records[0] = b` because the slice header is shared, which would otherwise recurse forever. The plan correctly checks depth "before descending". It should name this as a reason the check must come before recursion, and could add a one-line test that such input returns an error rather than overflowing the stack.
No blocker or major issue remains. The three round-1 majors are resolved in plan.md itself, not just claimed in the rebuttal: count-based allocation is bounded by `n <= (len(payload)-4)/9` and n is never used as an allocation capacity; supplemental tests cover the 8/9 depth boundary, inner-boundary crossing under a valid outer CRC, count and trailing-byte exactness, version 0 and v1 type-3 rejection, and a bad inner CRC; and the build target is worktree/walcodec.go with snapshot-v1 as a read-only reference. I re-derived the depth convention (sub-stream depth > 8 rejected; public case 7 opens depth 9), Encode always writing version 2 (the v1 public suite never asserts the version byte), and version-first validation from the amendment and both test files, and the plan is consistent with them.
