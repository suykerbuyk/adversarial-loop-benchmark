# Code findings — walcodec v2 (XtoC rep1, code review phase 2 round 2)

Verification (all re-derived from source, not from claims). No code_rebuttal.md exists. The implementor's turn log (turns/c2_2_imp.json, .err) shows the sandbox rejected the write ("writing outside of the project"), so I checked each round-1 finding against the code myself. In a scratch copy (/tmp/wc2) with go1.27.2: `go build`, `go vet`, and `gofmt -l` are clean. `go test -race -count=1 ./...` passes all 20 tests (v1 public, v2 public, and 4 new extra tests). Both public test files are byte-identical to instrument/.

Adversarial probes, all behaving to spec:
- Depth: 8 nested Batches (hand-built bytes) decode. An empty Batch opening depth 8 decodes; one opening depth 9 is ErrCorrupt in Decode. A cyclic (self-referential) Batch stops at the depth cap in Encode.
- Malformed inner frames: an inner len of 0, an inner len over 16 MiB, and an unknown type 4 are all ErrCorrupt.
- Encode inputs: a nested `*Put` and a nil Record both wrap ErrUnsupportedRecord. A Batch body of exactly 16 MiB round-trips; one byte more is ErrRecordTooLarge.
- Fuzzing: a 30 s Decode fuzz run (10.2M execs) found no panics, no input Decode accepts but Encode rejects, and no non-canonical v2 re-encoding.

Round-1 status: the ErrCorrupt text is restored to "walcodec: corrupt stream", the frame `len` is backpatched from emitted bytes, the hard-coded `frameSize(child, 1)` is gone, named constants and an allowedKind function are back, Encode errors carry the record index, the unused `counted` parameter and the dead trailing-bytes check are removed, a shared decodeFrame is used, Encode's godoc documents its errors and the depth cap, the Kind and Batch docs are back, and the output is presized. The round-1 major is mostly resolved by walcodec_v2_extra_test.go; the remaining test gaps are below.

minor: The supplemental "inner crossed batch boundary" test (walcodec_v2_extra_test.go:77-88) does not catch the bug it claims to guard. Its inner frame needs 28 bytes, but only 27 bytes exist from the inner frame's start to the end of the whole stream, so even a decoder that reads past the Batch into the outer stream fails with "truncated". Verified by mutation: changing the Batch loop to `decodeFrame(payload[pos:cap(payload)], ...)` with only a `pos < len(payload)` check (a decoder that over-reads into the enclosing buffer) passes ALL v2 public and extra tests. The amendment's key rule, "never a read into the next outer frame", therefore has no effective regression guard. Fix: a white-box test that calls `decodeBody(body[:len(body)-4], 0, 0, 2)` on a valid Batch body whose backing array still holds the inner CRC beyond the slice length. I checked it: it FAILS on the mutant and passes on the real code. Or build a black-box stream where the over-read bytes really would satisfy the inner len and CRC.
minor: Several items from plan.md's verification table are still untested. (a) An inner frame with `len` > 16 MiB ("cover inner-frame length cap"). (b) The plan wants the depth check proven "on entry regardless of n", but the empty-Batch-opening-depth-9 case is tested only through Encode (extra_test:26-36); Decode's matching check (walcodec.go:245) has no test. (c) The 8-level round trip checks only `err == nil` from Decode and never compares the decoded records with recsEq2, so a decoder that returns wrong contents at depth 8 would pass. (d) An inner len of 0 and a positive n=0 empty-Batch round trip are not covered. Behavior is correct today (my probes above), but a regression would pass acceptance. Fix: add these four cases to walcodec_v2_extra_test.go.
nit: There is no code_rebuttal.md, so round 1 got no point-by-point response, although the brief requires one. The cause is environmental (the sandbox rejected the write outside worktree/), not neglect, and the fixes above show every round-1 item was addressed in code. The process artifact is still missing.
nit: allowedKind (walcodec.go:213-222) runs before the `switch b[0]`, so the switch's `default: unknown record type` branch (walcodec.go:271-272) is unreachable. A genuinely unknown tag such as 4 in a v2 stream is reported as "record kind is not allowed for version", which is misleading. Adding a kind still means editing four places (allowedKind, decodeBody's switch, frameBodySize, appendFrame). Fix: say "unknown record type" when the tag is unknown in every version, and drop the dead default, or keep one per-kind table of encode/size/decode funcs.
nit: The encoder still has two independent type switches (frameBodySize and appendFrame). Backpatching the len removed the self-inconsistent-frame risk, but the 16 MiB cap and the uint32 casts are enforced only in frameBodySize. appendFrame has no `default` and would silently emit a body-less, len-0 frame for any type it does not handle. Today this is safe only because the pre-pass rejects such types first. Fix: add a `default: panic("unreachable: validated by frameBodySize")` in appendFrame, or merge size and emit into one per-kind helper.
nit: Two encoder bounds checks are unreachable on 64-bit hosts. `uint64(len(v.Records)) > MaxUint32` (walcodec.go:106) can never fire, because each child adds at least 13 bytes, so the 16 MiB body cap triggers first. The `total` int-overflow guard (walcodec.go:75) can fire only on 32-bit, and there it returns tooLarge() without the record index that every other Encode error carries. Fix: drop the dead count check or comment it as defensive, and wrap the overflow error with `record %d`.
nit: Nested Encode errors repeat the prefix once per level ("record 0: record 0: ... record 0: walcodec: corrupt stream: batch nesting exceeds 8", 9 times for a cyclic Batch) instead of giving one compact path such as "record 0.0.0...". This is readable but noisy; a path accumulator would be cleaner.

No blocker or major issue remains. Wire format, the version rule, the depth cap (both directions), exact-consumption and boundary enforcement, the 16 MiB cap at every depth, allocation bounds (the count is bounded by payload/9 with no count-driven preallocation), and v1 fixture compatibility are all correct, as verified above. The remaining items are test-strength and maintainability issues.
