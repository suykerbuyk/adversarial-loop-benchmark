minor: The encoder still has no early stop at the 16 MiB cap. This open minor finding from the plan review was not fixed. appendRecords (walcodec.go:52-135) checks bodyLen against maxFrameLen only after a Batch's children have been written. A Records slice that reuses the same child (legal Go) therefore expands far beyond the cap before it is rejected. Measured: a Batch of 100 copies of (a Batch of 1000 copies of (a Batch of 1000 Delete{})) is about 100 KB of Go structure. Encode returned errEncode only after 4.8 s, 6.8 GB of total allocation and 4.3 GB of process memory. One more 10x level would crash the process with a fatal out-of-memory error, which recover() cannot catch, on a call that was always going to fail. Fix: give appendRecords a size budget (stop once len(out)-bodyStart > maxFrameLen while writing children), or compute sizes first. Add a test with a reused wide Batch that must fail fast.
minor: The v2 rewrite deleted every doc comment that v1 had: ErrCorrupt, Record, Put, Put.Kind, Delete, Delete.Kind and Encode ("Encode writes recs as a version-1 stream"; diff against snapshot-v1/walcodec.go). The new exported Batch, Batch.Kind and Decode have none either. The stale Encode comment should have been updated to say version 2, not removed. The spec deliverable is "idiomatic, maintainable Go", the plan said "Update stale v1-only comments", and golint/revive would flag every exported symbol.
minor: There is no test beyond the shipped public suites, although the plan's validation map promised about 12 boundary tests. The most error-prone rule, that exactly 8 nested Batches are legal, has no test: public case 7 checks only that 9 are rejected, so an off-by-one that rejects 8 would still pass every shipped test. Also untested: encoder depth symmetry (8 succeeds, 9 errors), an empty Batch crossing into depth 9, Kind 3 in a v1 stream, count too large or too small, trailing bytes in a Batch, an inner len running past the payload while valid outer bytes follow, nil and typed-nil records at nested depth, and self-referencing input. I checked all of these by hand and they behave correctly today, but none is protected against future regressions.
minor: The bounds and CRC logic for reading a frame is written twice. decodeStream (lines 157-179) and the Batch loop in decodeBody (lines 197-219) each have their own copy, with different arithmetic (bodyLen+4 after advancing pos, against frameLen+8 before). The plan said to use "a function scoped to the current stream slice", and the plan review relied on one shared parser as the evidence that the cap is checked at inner depth. A future fix to one copy (for example a new limit) can silently miss the other. Extract a single readFrame(b []byte, pos int) (body []byte, next int, err error) used by both.
minor: In appendRecords, the Batch and *Batch branches (lines 75-111) are identical 18-line copies, and control flow is split by a later `if kind != batchKind` block that appends the Put/Delete body. Adding a record kind means editing three places. Normalize *Batch to Batch (and *Put/*Delete to values) at the top of the loop, then use one case per kind that writes its own payload.
minor: Encode errors carry no information. Every failure (nil interface, typed-nil pointer, unsupported type, depth over 8, a frame over 16 MiB, a count over uint32) returns the same unexported errEncode, "walcodec: cannot encode record". Under v1 a nil record returned the more specific "walcodec: nil record", so this is a regression. Callers cannot tell "too deep" from "too large" from "bad record", and errors.Is cannot be used. The plan review asked for one documented choice for the over-depth error (an unexported errTooDeep, or wrapping), and none was made or documented. Return wrapped errors with context, for example fmt.Errorf("walcodec: batch nesting exceeds %d", maxNestDepth).
nit: Empty slices come back inconsistently. A decoded empty Batch has a non-nil Records (make([]Record, 0), line 196), while the top-level empty stream decodes to a nil []Record and an empty Put.Value decodes to nil. As a result, reflect.DeepEqual(Decode(Encode(Batch{})), Batch{}) is false (measured). The plan's validation table said empty Batch decodes "with nil Records". Use `var children []Record` to match the plan and the other two cases.
nit: The depth check in decodeStream (`if depth > maxNestDepth`, lines 152-154) can never fire. decodeStream is only called from Decode with depth 0, and nested streams go through the decodeBody loop. Its depth parameter is always 0. Remove both, or route nested streams through decodeStream (see the shared-parser finding above).
nit: The minimum-frame bound uses an unexplained magic number, `uint64(len(remaining))/13` (line 192). The plan review asked for a named minFrameLen constant with a comment explaining where 13 comes from (4 len + 1 type + 4 empty key length + 4 crc). Without it, a future record kind with a smaller frame would silently reject valid streams.
nit: In the encoder, the check `uint64(len(key)) > uint64(^uint32(0)) || uint64(len(value)) > ...` (line 116) can never be reached in practice, because maxFrameLen (16 MiB) rejects anything that large first. The Batch count check (lines 80/100) has the same problem. They are harmless, but they hide that the frame cap is the real limit. Keep one cap check, made early as in the first finding.

Re-derivation notes (no finding): I built the code and ran gofmt -l (no output), go vet (clean), and go test -race on both public suites (17/17 pass, identical to the copies in instrument/). In a separate scratch copy I checked: 8 nested Batches encode and decode, 9 are rejected on both sides; an empty Batch at substream depth 9 is rejected on both sides; versions 0, 3 and 255 are ErrCorrupt; Kind 3 in a v1 stream is ErrCorrupt; count too large or too small, trailing bytes, a short count, an inner len past the payload with valid outer bytes after it, and an inner len over 16 MiB are all ErrCorrupt; n times 13-byte minimum frames decode exactly; nil interfaces, typed-nil *Put/*Batch, a nested nil and a self-referencing Batch return errors without panicking; decoded Values do not share memory with the input. A 45 s decode fuzz run (17.8M executions, seeded with v1 and v2 streams) found no panic, no error other than ErrCorrupt, and no case where a successfully decoded v2 stream failed to re-encode to identical bytes. The code has no shared mutable state, so there are no race concerns.

Summary: no blocker and no major issue remains. The implementation is correct against the amendment and the v1 regression rule. Six minor findings (no early 16 MiB stop in the encoder, carried over from the plan review and now measured at 4.3 GB; v1 doc comments deleted; promised boundary tests missing; duplicated frame parsing; duplicated Batch/*Batch encoding; uninformative encode errors) and four nits are open.
