minor: §2.3 step 5's child-guard failure is `fmt.Errorf("batch record %d: batch exceeds frame cap", j)` and then returns, so the index is the child that did not fit, while a child that fails inside appendFrame is wrapped as `batch record %d: %w` for that same child. Both shapes are legal under the single-prefix rule, but a later reader will treat "batch record N" as "N failed" in one path and "N could not be started" in the other, and §5 only checks the prefix, the count of "walcodec:", and !errors.Is. Name the guard message as a budget failure of the parent before child j, or document that j is the unwritten child, and assert that text in the child-guard case.
minor: §5's depth-2 table says each case's message contains `at offset <off>` and `(depth <d>)`, but it never says which depth that is. The construction is "one corruption of each kind at depth 2", and the depth-exceeded row is a Batch frame sitting in a depth-2 stream, whose own error is raised with corruptAt(off, depth, ..., depth+1) so the message says depth 2 while the rejected sub-stream is 3. An implementor who asserts `(depth 3)` for that row, or who puts the sub-stream depth in every batch error, still matches the prose and fails the convention in §2.2. State the expected depth per row, and for the depth-exceeded row require `(depth 2)` plus the text of the rejected sub-stream depth.
nit: §2.2's batch step 4 uses integer division, `uint64(n) > uint64(len(p))/minRecordFrame`, so a payload of 12 bytes accepts n = 0 only and a payload of 13 bytes accepts n = 1. The §5 "exactly fills" case uses 13-byte Deletes and never states that a remainder must not round the bound up. A later edit to `(len(p)+12)/13` would accept n = 1 in 12 bytes, allocate, then fail inside frame, and every listed count test would still pass. Add one case with len(p) = 13*k+12 and n = k+1.
nit: §5's cap-boundary helper derives vlen from outer len = 22 + len(k) + vlen and checks the outer len field, which pins the arithmetic.
