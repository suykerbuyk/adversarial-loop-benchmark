minor: The planned "Nested CRC flip" extra test (§Extra tests: "flip a byte inside an inner frame, recompute nothing, expect ErrCorrupt") cannot tell a correct decoder from a broken one. Every inner byte is also covered by the enclosing Batch frame's CRC, so the outer check rejects the stream first. An implementation that never verifies inner-frame CRCs (for example, a parseBatch that slices inner bodies without calling nextFrame's CRC step) still passes. The spec requires every frame at every depth to have the same [len][type][payload][crc] shape, and v1 says "Decode validates each frame's crc". Fix: build the stream with mkFrame2. Corrupt the inner frame's CRC (or its body), then re-wrap it in mkFrame2(3, batchPL2(...)) so the outer CRC is valid over the corrupted payload. Expect ErrCorrupt and a nil slice. Do this at depth 1 and at depth 8.
minor: The hand-built "inner len past the enclosing payload" and "inner oversize len" tests (§Extra tests) do not say how many bytes follow the count word. parseBatch's `uint64(n)*13 > len(rest)` pre-check runs before any inner frame is read. If the test's Batch payload has fewer than 13 bytes after n=1 (an easy shape for "a small payload"), the pre-check rejects it and nextFrame's span bound and inner cap check never run, so the test passes for the wrong reason. In the prototype, a 20-byte remainder was needed to reach the oversize path. Fix: require len(rest) >= 13*n in both tests. For the past-the-end case, make the inner len and CRC exactly right if they were read from the outer buffer, so the inner frame would decode cleanly if it took bytes from the following top-level frame. Only then does the test prove the decoder never reads past the span, not just that something failed.
minor: The amendment's general paragraph says "Nesting is capped at depth 8; a deeper nest is ErrCorrupt" without limiting it to Decode. The plan has Encode return errTooDeep, which does not wrap ErrCorrupt (§Depth, §Errors), and never cites or answers that sentence. The precise depth section only says the encoder "will not emit a stream it would itself reject" and names no error. So the reading is ambiguous, and a grader test of the form errors.Is(Encode(nine-deep), ErrCorrupt) would fail. errTooDeep is unexported, so outside callers cannot test for it; to them the only visible difference is whether the error wraps ErrCorrupt. Fix: either quote the sentence and record the decision (a non-wire error, consistent with errFrameTooLarge and errUnknownRecord) as a deliberate interpretation, or make the encode depth error satisfy both checks (fmt.Errorf("%w: %w", errTooDeep, ErrCorrupt)). Either way, pin the choice with a test.
minor: Encode's record-type dispatch is written twice (§Encode path: an inline child switch in appendBatch, plus Encode step 4: "The switch has the same nil and default arms as appendBatch"), and frameSize and decodeFrame add two more. A future kind 4 would need four coordinated edits, and the two write-path switches can drift apart silently, for example a new arm added at top level but not inside Batch. Fix: use one appendRecord(buf, r, depth) helper for both the top-level loop and appendBatch's children (the prototype does this and passes everything). That leaves one switch per pass (size, write, decode), and the size and write switches should sit next to each other in the file.
nit: The plan claims "On every error path, parseBatch and decodeFrame return a nil Record interface" (§Untrusted count), but its decodeFrame keeps v1's `return parsePut(body[1:])` / `return parseDelete(...)`. On error those return Put{} or Delete{} boxed into the interface: a non-nil Record that allocates. Measured in the prototype: a hostile-klen top-level Put gives AllocsPerRun == 1. Decode discards it, so behavior is unaffected, but the invariant as written is false, and a later zero-alloc test on a Put/Delete error path would fail unexpectedly. Fix: in decodeFrame, use `p, err := parsePut(...); if err != nil { return nil, err }; return p, nil` for kinds 1 and 2, or reword the claim to cover parseBatch only.
nit: The plan says the decoder struct makes "a later version ... a table change, not a signature change", but the kind/version rule it specifies is an inline `kind 3 only when version == 2` branch inside nextFrame/decodeFrame, which is not a table. Either add a small allowed-kinds lookup indexed by version, or drop the claim so the comment matches the code.
nit: For a codec that parses hostile bytes and will be maintained for years, the extra tests are all hand-picked cases. Add a FuzzDecode seeded with the v1 fixture, the public v2 streams, and the 8- and 9-wrap streams. Assert that Decode never panics, and that every stream Decode accepts with version byte 2 re-encodes byte-for-byte. That catches cursor and span regressions these examples will miss.
