# Code findings: walcodec v2 (GtoC/rep2), adversarial code review, phase 2 round 2
Checks I ran: I re-derived every claim from source after reading code_rebuttal.md. With go1.27.2, `gofmt -l`, `go vet` and `go build` are clean. `go test -race -count=1 -cover` passes at 89.6%. Both public test files are byte-identical to instrument/. FuzzPrivDecode ran 45s (about 17.6M execs) with no failure. All 8 round-1 rebuttal items are verified as applied: the white-box spill test exists and passes; `decodeFrame` uses a three-index body slice, and `capSlice` caps the stream, the payload and Batch `rest`; Encode's depth error is bare ErrCorrupt (`==` holds); the TooLarge comment was corrected; the Batch nil/empty doc was added; TestPrivKindValues exists; appendClosedFrame returns only `[]byte`; the kind bitmask replaces allowBatch; the per-frame CRC comments are present. I checked production behavior directly. Versions 0 and 3 are rejected and versions 1 and 2 accepted. Batch in a v1 stream is rejected. 8 nesting levels are accepted and 9 rejected, the same in Encode and Decode, including an empty Batch at depth 9 and a self-referential slice. A Batch body of exactly 16 MiB encodes and decodes; one byte more returns errTooLarge, not ErrCorrupt, with nil output. A top-level len of exactly 16 MiB is accepted. 12 hand-built CRC-valid malformed frames all return ErrCorrupt with no panic: Batch payload under 4 bytes, klen/vlen overrun, Put or Delete trailing bytes, inner len 0 or 0xFFFFFFFF, inner type 0 or 99, and a bad inner CRC. I ran 16 mutants against the full shipped suite; the 10 survivors are listed below.
minor: TestPrivBatchNMaxUint32 does not check the property plan item 5 says it checks ("ErrCorrupt without a huge allocation"). I removed the guard (`if uint64(n) > uint64(len(rest)/minWireFrameBytes)` replaced by `if false`). The whole suite still passed, and a probe measured TotalAlloc going up by 65536 MiB, because `make([]Record, 0, 0xFFFFFFFF)` gets 64 GiB of untouched virtual memory under Linux overcommit, so it fails later as ErrCorrupt. The production guard is correct, so this is a missing regression guard and not wrong output. I rate it minor, not major like round 1's spill issue, because the amendment does not state this rule; it comes from the plan's own robustness rule. Fix: in that test, read runtime.MemStats.TotalAlloc before and after Decode and assert the increase is under about 1 MiB.
minor: Nothing tests the Batch 16 MiB cap on Encode, which plan item 3 requires ("16 MiB cap at every depth"). The in-loop check and the final check in appendBatchFrame back each other up, so removing either one alone changes nothing. I removed both and the full suite still passed, while Encode of a Batch with a 1-byte-too-large body returned a stream with err == nil whose outer len is over 16 MiB, which its own Decode rejects. That breaks the self-consistency rule the amendment states for depth. Coverage shows encode.go:125 and :130 never run. Fix: add a test that encodes a Batch body of exactly maxFrameLen (it must round-trip) and maxFrameLen+1 (it must return non-nil, non-ErrCorrupt err and nil bytes). That is about 32 MiB of allocation, which is the same cost class as TestPrivTooLargeIsNotCorrupt.
minor: Each nesting level preallocates `make([]Record, 0, n)` with n bounded only by its own payload/9, and every enclosing level's slice stays live while children are decoded. So a single CRC-valid frame amplifies memory about 15x before it is rejected. My probe built 8 nested Batches, each claiming n = len(rest)/9 with the next level as its only real child, around one large Delete. A 15 MiB input made Decode allocate 243 MiB (44 MiB for 1 level), then return ErrCorrupt. The cost is bounded and linear, so I rate it minor, but a WAL decoder reading damaged or hostile files should not do this. Fix: cap the preallocation (for example `min(n, 1024)`) and let append grow it, since append is bounded by the frames that actually parse. Or at least divide by the smallest valid frame (13 bytes: an empty-key Delete or an empty Batch) instead of 9.
minor: The committed tests and the fuzz net never reach the CRC-valid malformed-payload paths. Under `go test`, these mutants survive: dropping Put's trailing-bytes check, takeString returning success on a klen overrun, takeBytes returning a slice that aliases the input (the "decode copies, no aliasing" rule in plan line 32), and changing the decode len cap to `> maxFrameLen+100` or `>= maxFrameLen`. The v1 TestOversizeLen pairs len 16 MiB+1 with a truncated body, so the truncation check alone rejects it; no test accepts len == 16 MiB. Coverage shows decode.go:118, 147-166 and 172-193 never run. FuzzPrivDecode does not cover this either. I fuzzed the put_trailing mutant for 30s (12.4M execs, "new interesting: 0") and it was not caught, because random byte mutations almost never produce a valid CRC, so the fuzzer barely gets past the CRC check. Fix: add a table test of hand-built CRC-valid malformed frames (the 12 I probed above), an exact-cap len acceptance case, and a test that mutates the input after Decode and checks the decoded Value is unchanged. Also make the fuzz target structure-aware: recompute every frame's CRC (and the inner ones) on the fuzzed bytes before calling Decode, so payload parsing actually gets fuzzed.
nit: Decode checks the version twice. The `if version != version1 && version != version2` early return is followed by a `switch` with a `default: return nil, ErrCorrupt` that can never run (decode.go:31 is uncovered). decodeFrame's `default:` case (decode.go:108) can never run either, because kindAllowed already filtered the tag. Keep one source of truth, either the switch or a version-to-mask table, and drop the dead branches.
nit: The bitmask comment in Decode says adding a kind is "a one-place change to the mask". In fact a new kind still needs a constant, a Kind method, an encoder case in appendFrame, and a decoder case in decodeFrame's switch, and the uint8 mask silently refuses any tag of 8 or more. Reword the comment so the next maintainer is not misled.
nit: plan/plan.md is out of date with the code. Line 300 still says Encode returns wrapped ErrCorrupt for the depth cap. Line 341 still says TestPrivTooLargeIsNotCorrupt shows the call "returns before copying the value". Line 242 still names `allowBatch`. Update the plan or mark it superseded, so a reader does not trust stale claims about errors and test coverage.
No blocker and no major issue remains. The production code met the amendment on every rule I checked, and every round-1 finding is fixed as the rebuttal describes. What remains is regression-guard gaps (an allocation guard, the Batch encode cap, CRC-valid malformed payloads, a weak fuzz target), a bounded ~15x memory amplification on rejected nested input, and documentation cleanups.
