major: The plan's only guard for the rule "an inner len that extends past its enclosing payload is ErrCorrupt (truncated), never a read into the next outer frame" cannot catch the bug it is meant to catch. TestPrivInnerLenDoesNotSpill (and the matching "inner-len spill" fuzz seed) sets the inner len to "the bytes left in the outer stream". But a frame also needs 4 CRC bytes after len, so that frame is truncated even when measured against the whole outer stream. The plan also never requires a valid inner CRC at the spill position. So a decoder that wrongly bounds the inner frame by the outer buffer still returns ErrCorrupt, from truncation or a CRC mismatch, and the test passes. Plan line 169 makes the same mistake ("fails inside the payload slice"): it fails outside the slice too. This matters in Go in particular. `payload` is a subslice of `b`, so its cap runs to the end of the outer stream. A refactor that drops or weakens the `frameLen > len(buf)` check, or reslices with `buf[:x]` up to cap, silently reads sibling or outer bytes without panicking. Nothing in the planned suite would catch that. Fix (1): build the test so that only the bound check can reject it. The bytes after the Batch payload must form a valid completion of the inner frame: the inner body spans the outer CRC plus chosen extra bytes, and a correct inner CRC follows. This is not circular, because the outer CRC does not cover the inner CRC: compute the outer body and its CRC first, then the inner CRC. The simplest robust form is a white-box test in the internal file. Call the batch-payload decoder on `buf[:k]`, where `buf[k:]` completes the inner frame with a valid CRC and a parseable Put payload, and require ErrCorrupt. Also assert the end-to-end form does not panic. Fix (2): hand child parsers capacity-capped slices (full slice expressions, e.g. `body[1:n:n]` and the Batch `rest`). Then any accidental reslice past the enclosing payload panics instead of silently reading the next frame.
minor: For the depth cap, Encode returns ErrCorrupt wrapped (`fmt.Errorf("%w: batch nesting exceeds depth 8", ErrCorrupt)`). The amendment does not fix the encode error identity. A hidden grader written in the style of the reference might compare with `err == ErrCorrupt` as well as `errors.Is`. Bare ErrCorrupt satisfies both, and the wrap gives callers nothing they can check in code beyond what `errors.Is(err, ErrCorrupt)` already gives (the plan admits this is "the caller-visible distinction"). The decode side already returns bare ErrCorrupt for exactly this reason. Fix: return bare ErrCorrupt from the encoder's depth check, keep the context in the doc comment, and pin `errors.Is` (and `==`) in TestPrivDepth9EncodeRefused.
minor: TestPrivTooLargeIsNotCorrupt says "the call returns before copying the value", which a unit test cannot check reliably. Checking it with runtime.MemStats or AllocsPerRun around a 16 MiB+ buffer is flaky under GC and parallel tests. Leaving it out makes the plan's line an unverified claim. Fix: assert only that the error is non-nil and `!errors.Is(err, ErrCorrupt)` and the returned bytes are nil. Enforce the size-first ordering by code structure (putBodyLen/deleteBodyLen called before any append) and a review note, not a test assertion. Or, if a test is wanted, use `testing.AllocsPerRun` with a pre-allocated oversize Value and a loose bound, documented as best-effort.
nit: The appendBatchFrame pseudocode never handles a child's error: `dst = appendFrame(dst, rec, childDepth)` is followed straight by the size check. A literal translation would drop the error, or measure bodyLen on a nil dst, which hides a depth-9 or errUnsupported failure as errTooLarge or a slice panic. State explicitly: `dst, err = appendFrame(...); if err != nil { return nil, err }` before the running size check. The same applies to the payload-writer closure in appendClosedFrame, if it can fail.
nit: Plan line 81 shows the bound as `n > uint32(len(rest)/minWireFrameBytes)`. Line 84 then says to compare in uint64. Two forms of one check invite copying the wrong one. Show only `uint64(n) > uint64(len(rest)/minWireFrameBytes)` in the code block.
nit: "Adding a future version is a one-place change in Decode" overstates the `allowBatch bool` design. A future version that adds a fourth kind needs that bool replaced by a kind set and threaded through decodeStream/decodeFrame/decodeBatchPayload. Either keep the bool and soften the claim, or pass a small unexported `kinds` bitmask (or per-version value) now, so the signatures do not change later.
No blocker remains. One major issue remains: the inner-len spill regression test, as written, cannot catch the bug it targets. The other findings are minor or nit.
