minor: The revised takeBytes sketch still panics on a payload shorter than 4 bytes, so truncated Put and Delete payloads do not return ErrCorrupt. snapshot-v1/walcodec.go:216 and the plan's required order both start with `if i < 0 || i > len(payload)-lenSize`. In Go that subtraction is evaluated before the comparison. When len(payload) < 4, `len(payload)-lenSize` wraps, `i >` that wrapped value is false for a non-negative i, and execution falls through to `payload[i:i+4]`, which panics. The plan then says `avail = len(payload)-(i+lenSize)` is safe because `i <= len-4`. That premise is false for a short payload, and the sketch never checks `len(payload) < lenSize` before subtracting. A truncated Put or Delete payload is a corrupt frame: v1 requires a truncated frame to be ErrCorrupt, and the amendment keeps every v1 decode behavior. The public suite does not build a 1-byte payload, so `go test` stays green while a hand-built short payload panics. Guard with `len(payload) < lenSize` (and `i < 0 || i > len(payload)-lenSize`) before any subtraction, then do the uint64 compare, then narrow n to int.
