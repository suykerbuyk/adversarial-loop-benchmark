minor: Waking waiters early changes the order rule 8 describes, and nothing documents or tests that choice. The spec states Close's order twice: in the interface doc ("cancels in-flight loads, waits for their Loader calls to return, wakes every waiter with ErrClosed, drops all entries") and in rule 8 ("cancels..., waits for every in-flight Loader call to return, wakes every current waiter..., drops all entries"). The round-2 plan closes `closedCh` and drops entries in Close's first critical section, before cancel() and loaders.Wait(). So a waiter can get ErrClosed, and Len() can read 0, while the Loader is still running. A test that reads the order literally (a waiter gets ErrClosed, then it asserts the Loader has already returned) would fail. The round-1 finding suggested a lighter fix: a waiter woken by its own ctx checks `closed` (under mu or via an atomic) before returning ctx.Err(). That fix keeps the spec's order for waiters whose ctx is still live. If eager waking stays (it is what lets the own-key Get with context.Background() finish), state in Close's doc comment that waiters are released at the start of Close, before the join, and why. Also add a test that pins this behaviour, so a future maintainer does not "fix" it back to the other order.
minor: runLoad is not safe against runtime.Goexit, so a single key can be stuck forever. Only `loaders.Done()` is deferred. The resolution (lock, delete(inflight,key), set cl.err, close(cl.done)) runs as straight-line code after callLoader returns. If a Loader calls runtime.Goexit (t.FailNow/t.Fatal inside a Loader, or a library that calls Goexit), recover() returns nil, callLoader never returns, and the goroutine ends with `inflight[key]` still set and `cl.done` never closed. From then on, every Get for that key joins a dead call. A Get without a deadline hangs until Close. This contradicts I2 and the plan's claim (§4) that waiters are never stranded. Fix: do the resolution in a deferred function, with a `normalReturn` flag like x/sync/singleflight. A Goexit or panic then resolves the call with an error (for example an `errGoexit` or *PanicError) on every exit path.
minor: The ErrSelfGet check gives false positives and overrides ErrClosed. It runs before the closed check and before the hit lookup, and it fires for any ctx derived from the Loader ctx, including after that load has finished. (1) A Loader may hand lctx, or a ctx derived from it, to a goroutine that outlives the call. A later Get(key) on that ctx returns ErrSelfGet even though the key is now resident. That breaks rule 1 ("key resident: return a copy"). (2) After Close, a Get with a tagged ctx returns ErrSelfGet instead of ErrClosed. That breaks rule 8 ("A Get that has not yet passed the closed check returns ErrClosed") and the rule 7(a) priority. Fix: store the *call (not just the key) in the tag. Under mu, after the closed check and the hit lookup, return ErrSelfGet only if `inflight[key] == tag.call`. That condition is exactly "this Get would wait on itself".
minor: The new priority tests (13 and 14) never exercise the post-wake resolution order they are meant to protect. In both variants of TestCloseWindowPriority, Close runs before the waiter's deadline, so the waiter is woken by `closedCh` alone. You could delete the closed → done → ctx re-check, or reorder it, and the tests would still pass. Add a case where ctx.Done and closedCh (and, separately, cl.done and closedCh) are both ready when the waiter's select runs. In synctest, park the waiter, then from the root goroutine cancel the waiter's ctx and call Close (in a goroutine), then synctest.Wait(). Repeat it with -count so both select branches get picked. Assert ErrClosed every time. Also make test 13 park the waiter with synctest.Wait() before starting Close. Otherwise the waiter can hit the closed check in Get and pass without ever waiting.
nit: The ctx.Value(loadTagKey{}) lookup is the first statement of Get. It walks the whole context chain on every call, including the hot hit path, so its cost grows with ctx depth and is paid by every caller to catch a rare misuse. Moving it into the miss/join branch under mu (see the ErrSelfGet finding) also fixes this.
nit: PanicError.Error() puts the full stack into the message. Every log line or wrapped error that prints err then carries a multi-kilobyte stack, and the same stack is repeated for every waiter of that load. Keep Error() to one line ("blockcache: loader panicked for key %q: %v") and leave the stack in the Stack field, which callers can read through errors.As.
nit: The tag value holds a *cache, and user code can keep lctx alive past the load, which keeps the whole cache (entries map and lru) reachable. Tagging with the *call alone (it has no back-pointer to the cache) is smaller, and it is the same value the ErrSelfGet fix needs.
nit: Go 1.25 has sync.WaitGroup.Go. Plain `loaders.Add(1)` under mu plus `defer loaders.Done()` is still correct and keeps the "Add only under mu while !closed" invariant visible, so this is optional. Just keep the comment that says the Add must stay under mu.
No blocker or major issue remains. I re-derived each point from the spec and the public tests. Single-flight runs through the inflight map under mu. Bytes are copied on admission and on every return, and (nil,nil) gives a non-nil empty slice. The error wins over bytes and is never stored. Eviction and admission happen in one critical section, so Len() <= capacity even under a concurrent poll. An in-flight load is not in lru, so it is neither counted nor evictable. Recency is updated on a hit and on a load. The Loader runs under a cache-scoped ctx and orphaned loads still populate the cache. Rule 7 priority now holds in the Close join window: closedCh is closed together with `closed`, and the post-wake order is closed → done → ctx. WaitGroup.Add happens only under mu while !closed, so Wait cannot race it. Results that arrive late or after Close are discarded through the `closed` check in runLoad. A second Close joins via closeDone. mu is never held while blocking, and every wait is channel-only, which synctest treats as durably blocked. All eight public tests should pass under -race, including TestSingleFlight's synctest.Wait checks. The findings above are robustness, test-strength and documentation gaps.
