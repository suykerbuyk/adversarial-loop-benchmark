minor: run() handles only panics (safeLoad's recover) and does not handle a Loader that exits through runtime.Goexit (for example t.FailNow/t.Fatal inside a test Loader, or any library that calls Goexit). Only the deferred loads.Done runs, so the delete(inflight, key) and close(cl.done) steps are skipped. The key then stays in inflight forever: every later Get for it joins a dead call and blocks until its ctx expires or Close runs. That breaks rule 2/3's "a later Get re-loads" and is a practical liveness trap. Fix: do the resolution (delete inflight, set err, close done) in a defer guarded by a "returned normally" flag, as x/sync/singleflight does, so every way of leaving the Loader resolves the call.
minor: Turning a Loader panic into an ordinary error is an undocumented policy change that hides programmer bugs and drops the stack trace. The plan's reason ("the process would usually crash anyway") is wrong: an unrecovered panic in the run goroutine always crashes the process. Either re-panic after cleanup (x/sync/singleflight passes the panic on to the waiters), or keep the recover but put the stack (runtime/debug.Stack) in the error and state the policy in the package doc. Do not describe it as harmless.
minor: Close wakes waiters with ErrClosed before loads.Wait(). Rule 8 lists the steps as cancel, then wait for every Loader to return, then wake waiters. Rule 7(a) allows early waking, but a hidden test that asserts "the Loader has returned by the time a waiter sees ErrClosed" would fail. The plan should either follow the spec's listed order (close closedCh after loads.Wait; waiters still wake promptly because a Loader that honours its contract returns as soon as ctx is cancelled) or justify the deviation explicitly in the code comment and add a test. Recommended: follow the spec's order. It costs nothing for Loaders that honour their contract and removes the ambiguity.
minor: The plan copies the bytes while holding the single global mutex, both on hits (clone(el.val) under mu) and in run (clone(val) before admit). The blocks may be large, so every Get and every completion is serialized behind memcpy. entry.val and call.val are immutable, so the hit copy can happen after mu.Unlock, and run can clone the Loader's slice before taking mu. This is a long-term performance and maintainability issue, not a correctness one.
minor: Internal test 4 ("orphaned load populates the cache: Len()==1" after release) has no waiter left to synchronize on, and rule 5 allows Len to lag a completion. Asserting Len()==1 right after releasing the Loader is racy unless the test is inside a synctest bubble and calls synctest.Wait() first, or polls with a deadline. The plan must say which. The same applies to test 7's "Close blocks until release" negative check, which needs synctest.Wait to be meaningful.
nit: Internal test 5 ("resolved beats ctx") cannot make the race deterministic even with synctest: once cl.done is closed and ctx is cancelled, select picks a ready case at random. The test sometimes exercises the re-check and sometimes doesn't, so it gives no reliable coverage. Unit-test wait()'s priority logic directly instead: pre-close done, pre-cancel ctx, then call wait. That is deterministic and covers the (c)-over-(b) branch.
nit: admit()'s "defensive" overwrite-if-resident branch is unreachable under I2 (only the call that owns the inflight entry stores the key, and closed-state stores are discarded). Dead branches obscure the invariant. Replace it with a comment, or with a panic/assertion that I2 holds, so a future violation surfaces.
nit: closed (bool) and closedCh duplicate the same state (I3). Keeping both is fine, but one should be derived from the other, or the doc comment should say that closed is the fast path read under mu and closedCh is for select. Otherwise a future edit may update one without the other.
nit: I6 says no slice is "aliased by entry.val or call.val", but admit(key, own) and cl.val = own deliberately share one backing array. That is safe because both are immutable and every reader clones, but the invariant should be worded to allow it, so a future change that mutates entry.val in place (e.g. an update API) doesn't silently corrupt in-flight waiters.
nit: The plan doesn't say the exported identifiers will carry the spec's doc comments (Loader contract, Get copy semantics, Len lag, Close idempotence), and it lists the re-entrancy restrictions only in passing. Godoc on Loader/Cache/New should state them.
No blocker or major issue remains: the design satisfies rules 1-9 as re-derived from the spec, including single-flight under mu, resident-only capacity with LRU eviction in one critical section, (a)>(b)>(c) wait priority via re-checks, WaitGroup Add only while open under mu, discard on close via the closed check under mu, and an idempotent Close joined through closeDone. It also passes the public suite as designed, including synctest TestSingleFlight.
