# Rebuttal of plan findings

Point-by-point response to `plan/plan_findings.md`. Each item is fixed in `plan/plan.md`, except one clause of the blocker, which is rebutted.

1. **blocker: the wait path is not durably blocked under Go 1.25 `testing/synctest`, so `TestSingleFlight` fails.** Fixed in the way the finding requires for the park. Waiters block only on `<-f.done`. `f.done` is created on the `Get` goroutine, inside the bubble in `TestSingleFlight`. `ctx.Done()` is not a select case. `Get` does not call `context.AfterFunc`.

   Rebutted, the clause that says to observe caller cancel with `AfterFunc` on a context whose `Done` channel was created in the bubble. Production `Get` cannot tell whether the caller's `Done` channel was created in a bubble, and `internal/synctest` is not available to the package. `AfterFunc` starts `go f()` from `afterFuncCtx.cancel`, not on the `Get` goroutine. Registered on a non-bubble caller ctx, that goroutine is outside the bubble: closing a per-waiter channel from it is an outside event, the select is not durable, and closing a bubbled channel from outside the bubble panics. `TestSingleFlight`'s `WithTimeout(t.Context(), 5s)` happens to be bubbled on Go 1.25, so `AfterFunc` on that particular ctx would not fail that one test. The same `Get` must also accept an ordinary caller ctx. One wait path serves both, and that path receives only on `f.done`.

   Rule 7(b) stays in `decide`, under `mu`, and is reached by a pre-check: if `ctx.Err() != nil` before the receive, `wait` does not park and returns `decide`. An already-cancelled ctx therefore gets `ctx.Err()` while the load is still `flightPending`, unless `closed` or a terminal publish already won. A cancel that arrives after the waiter has parked is applied when `f.done` closes. By then the flight is terminal, so `decide` returns `ErrClosed` or the load result, which is the spec order at decision time. Adding `AfterFunc` or `ctx.Done()` back into `wait` reintroduces this blocker for any non-bubble caller.

2. **major: Close's wake-then-Wait order deadlocks rule 8.** Fixed. On the close transition, under `mu`, Close sets `closed`, detaches every `inflight` entry, and publishes `flightDiscard` for flights still pending. It does not `close(done)` in that section, and it does not call `cancel` or `loads.Wait` while holding `mu`. It unlocks, then `cancel()`s the cache context, then closes `done` for the flights it moved to `flightDiscard`, then `loads.Wait()`. Waiters stay on `f.done` (a durable block when that channel was created in the bubble) until after unlock. When they wake, `mu` is free, so they are not stuck in `Mutex.Lock` while Close is in `Wait`. A Loader blocked on `<-c.root.Done()` observes `cancel` after Close has unlocked, takes `mu`, and `publish` no-ops because `state != flightPending`. `root` is `context.WithCancel(context.Background())`, so `cancel` closes `Done` synchronously and does not need the fake clock.

3. **minor: `decide` returns `clone(f.val)` for `flightOK` and never touches the LRU.** Fixed by stating the constraint on `decide` itself. A joined success does not move the element. Rule 6's recency write stays in the hit path (`MoveToBack`) and in `admit` (`PushBack`). `decide` must not look up an entry `publish` has not inserted, and must not take a second lock to touch.

4. **nit: `publish`'s closed check is `root.Err() != nil` as well as the `closed` flag.** Fixed. Discard is keyed only off the `closed` flag set in the close section. `root.Err()` is a consequence of that flag (`cancel` runs only after `closed` is set, and only on the close transition), not a second reason to publish `flightDiscard`.
