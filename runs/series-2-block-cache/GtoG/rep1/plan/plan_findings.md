blocker: A panic inside the admit section while run holds mu kills the flight goroutine without publish, so f.done stays open and inflight keeps the key forever. loads.Done is deferred and still runs, so Close can pass loads.Wait, but every waiter of that flight is blocked in select on f.done, ctx.Done, and started. If their caller contexts are not already done, they never return; rule 9 forbids that deadlock. A later Get of the same key finds the stale flight, does not start a new Loader, and joins the same never-closed channel, so the key is poisoned for the life of the process. The plan names this path (evictLRU, linkMRU, publish, map insert) and says f.done may still be open, then treats it as an unswallowed cache bug. An unswallowed bug is not a join protocol. publish, including the failure publish that closes f.done and deletes inflight, must run on the way out of that section, and mu must be unlocked before the goroutine dies. The inner recover does not cover this section because it returns before Lock.
major: Close documents that a Loader Done callback may call Close, then implements that re-entry as a self-deadlock. The owner sets closed, unlocks, and calls cancel while the Loader is still inside load and has not yet returned to run. A Done func that calls Close takes the non-owner path and blocks on joined. joined is closed only after loads.Wait, and loads.Wait cannot finish until load returns. The callback is running on the Loader goroutine, so load cannot return until the callback returns. The plan's restriction ("may call Close only if it does not need the Loader to return") does not remove the cycle: that Close always waits for this Loader to return. The same cycle exists for a parent of root whose Done func calls Close. Get and Len from that callback are safe; Close is not, and the sketch still invites it. Either forbid Close from a Loader-context Done func, or make the non-owner Close return nil once closed is set without waiting for joined while the caller is the flight goroutine.
minor: A cache-internal panic after Lock also skips the explicit Unlock, so mu stays locked when the goroutine dies. Every later Get, Len, and Close blocks on mu forever, including the Close that the plan says can still finish the join via loads.Done. Unlock has to be guaranteed for the same section that must publish on the way out.
nit: The wait-loop prose says a resolved load is returned only when the waiter is not observing closed, but the Get sketch returns f.err whenever closed is false in that section, including a discarded success published as (nil, nil). Those two agree only because the plan also claims root is cancelled solely by Close, so (nil, nil) cannot be published on an open cache. A later edit that cancels root for any other reason would hand waiters a nil-nil success for a value that was not stored. Tie the return of a nil error to "admitted or not closed," not only to the current cancel policy.
