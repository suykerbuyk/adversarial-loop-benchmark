minor: wait (plan §3.1) treats a closed cl.done as always winning over a caller's ctx.Done(). Rule 7's order is (a) ErrClosed if the cache closes, else (b) ctx.Err() if the caller's ctx is Done while the load is still in flight, else (c) the load result once resolved. "Still in flight" is a state of the load, not a claim that the waiter observed done after its ctx became Done. If both cl.done and ctx.Done() are ready, the second select returns the payload even when the caller cancelled first and the load was still running at that moment. That violates 7(b) for every cancelled waiter that loses the scheduling race to complete. After ruling out closing, if ctx.Done() is ready return ctx.Err() unless the load had already resolved before that ctx became Done (sample both under one observation, or record resolution time vs ctx.Done()). Do not let a late close(done) erase a cancellation that happened while the load was in flight.
minor: Close (plan §3.5) sets closed, closes closing, and drops items, then unlocks, then calls cancel(). Rule 8 cancels the cache-scoped context and discards a Loader result that returns after that context is cancelled. A Loader that returns in the window after closed is set and before cancel() runs is discarded because of the closed flag, but it returned against a context that was not yet cancelled, so the spec's stated discard condition does not cover it. If the Loader is slow to observe Done, Close still waits, but the window is a real gap between "drops all entries" and "Loaders have been cancelled". Call cancel while still holding mu, immediately after closed = true and before unlock, so every completion that observes closed also observes a cancelled cache context. cancel is safe under mu: it only closes the context's done channel and does not call the Loader.
nit: I3 says active == len(inflight) whenever mu is not held, but Get inserts the inflight entry and increments active, unlocks, and only then the spawned goroutine runs (plan §3.1–§3.2). Between unlock and the goroutine's start, active counts a load whose Loader has not been entered. Close's <-drained still waits for complete, so rule 8's join holds, but the comment overclaims and will mislead a later edit that treats active as "Loader currently inside c.load". Phrase I3 as "active equals the number of load goroutines that have been started and not yet completed", and keep the join proof on complete, not on Loader entry.
nit: callLoader recovers every panic from the Loader, including a runtime panic raised by cache code if someone later inlines admit or a map write into that defer's scope (plan §3.2). The current split keeps complete outside recover, which is right, but the recover body does not distinguish a Loader panic from a runtime panic (nil dereference, close of closed channel, index out of range). Those become a formatted error, the key is left uncached, and the process stays up, so a cache bug in that scope is silent forever. Recover only when the stack shows the panic originated in the Loader call, or re-panic runtime.Error values after complete has published an error to current waiters, so a cache bug still crashes.
