minor: The plan never says that synctest-based extra tests (1-5, 9, 14, 16) must build the cache, caller contexts and release channels inside the synctest.Test closure. Only test 16 mentions the bubble. If New runs outside the bubble, loadCtx.Done() is an unbubbled channel. A waiter's select (f.done, ctx.Done, loadCtx.Done) then does not durably block, so synctest.Wait never returns and, because the fake clock never moves, the 5s deadline never fires. A WaitGroup used from both inside and outside a bubble is also a runtime fatal ("sync: WaitGroup.Add called from inside and outside synctest bubble", src/sync/waitgroup.go). Fix: add one sentence to "Test approach": every synctest test calls New, creates its contexts (from the bubble's t.Context()) and makes its gate channels inside the bubble, and never shares a cache across bubbles or with non-bubble code.
minor: Extra test 12 ("coalesced waiters each get a private copy") does not force the two Gets to overlap. There is no synctest.Wait (or similar barrier) before release. The second Get can arrive after the load has finished and be a plain hit. The test still passes (count 1, equal bytes), but it then never checks the rule-2/rule-4 promise that each coalesced waiter gets its own copy, which is what its title says it checks. Fix: run it in synctest.Test. Start both Gets, synctest.Wait, assert Loader count == 1 with t.Errorf while both are parked, then close release.
nit: Extra test 13 says "a Loader that fails the test if called". The Loader runs on a cache-owned goroutine, so the plan should say t.Errorf, not t.Fatalf/FailNow (FailNow must run on the test goroutine; vet's testinggoroutine check may flag it depending on its shape). Say this explicitly, as the plan already does for the parked-goroutine rule.
nit: The "Test approach" text says "No extra test calls synctest.Wait while a goroutine is blocked on a mutex", and that a mutex wait is why sync.Once fails. That is too broad. synctest.Wait is fine while a goroutine briefly waits for mu, because the holder soon releases it and synctest.Wait simply keeps waiting. The real hazard is a mutex whose holder is itself durably blocked, as in sync.Once.Do around wg.Wait. Every Close test (4, 14, 16) already has woken waiters briefly taking mu around a synctest.Wait, so as written the rule contradicts the plan's own tests. Reword it so a future maintainer does not "fix" a non-problem.
nit: Extra test 17 limits outcomes to nil, ErrClosed or the Loader's error, but each Get uses a real 5s deadline context (no synctest). On a very slow -race CI host, a correct implementation could return context.DeadlineExceeded. Either allow ctx.Err() as an outcome, or keep the deadline only as an outer watchdog and give the Gets context.Background().
nit: Rule 4 says "every Get returns a fresh copy", but the plan stores and returns a successful (nil, nil) load as nil (extra test 7). That is a reasonable reading, since there are no bytes to copy and nil cannot alias, but it is an interpretation. The clone doc comment should name it as the one deliberate choice where the spec is silent, so a later reader does not "fix" it to []byte{}.
