minor: The panic-retry branch in `publish` (plan lines 185-221) can delete another flight's slot. `publish` runs `delete(c.inflight, f.key)` without checking ownership. Suppose the first `publish` panics after that delete but before the insert. The deferred `Unlock` releases `mu`, and a new `Get` can then see a cold miss and insert `inflight[key] = f2` with a second Loader call. The finisher's retry `publish(f1)` then deletes `f2`'s slot. `f2`'s goroutine is still running but no longer in `inflight`, so a third `Get` starts `f3`. That breaks single-flight (rule 2). The path is hypothetical, but this is the exact path the branch exists to handle. Fix: `if c.inflight[f.key] == f { delete(c.inflight, f.key) }`. Better: delete the retry branch entirely (see the next finding).
minor: The machinery for "panic inside publish" has no real trigger, and it complicates the one concurrency-critical function. Under the plan's own invariants, `publish` does only map and pointer writes and one small allocation. In Go, out-of-memory and concurrent map writes are fatal runtime errors, not recoverable panics. So the `entries[f.key]` retry branch, the "do not evict again" note, and line 159's "an allocation failure cannot leave mu held" defend against something that cannot happen, and no private test can exercise them. A future maintainer will have to reason about code that is dead and also subtly wrong (previous finding). Keep `defer mu.Unlock()` and the `published` flag, which Goexit and Loader panics really need. Drop the retry-after-partial-insert branch and its prose.
minor: The test list has no concurrent stress test, so `go test -race` never sees the interleavings rule 9 is graded on. Every one of the 17 private tests is a scripted, mostly sequential synctest scenario. Add one `TestImpl_...` stress test, with no synctest and no sleeps, bounded by a deadline: N goroutines doing `Get` over a small key space larger than capacity, with Loaders that sometimes error, sometimes block on ctx, and callers that sometimes cancel. A poller asserts `Len() <= capacity` on every read, and `Close` is called from two goroutines partway through. Afterwards assert that every `Get` returned bytes for its own key, a Loader error, `ctx.Err()`, or `ErrClosed`; that `Len() == 0`; and that the Loader in-flight counter is 0 once `Close` returns. This is what checks "never above capacity even under a concurrent poll" and "waits for every in-flight Loader call to return" under the race detector.
nit: Lines 252 and 262 (and the rebuttal) say `wg.Done` as the outer defer means "Close cannot stick" if the finisher's own `publish` panics. That panic is unrecovered on a non-main goroutine, so the whole process crashes and the claim is moot. Reword so maintainers are not misled about what the outer defer guarantees: it guarantees `wg.Done` on Loader panic and Goexit, not survival of a second panic.
nit: Line 182 says `publish` "does not allocate", but its success branch does `&entry{...}`, and line 221 then talks about "the entry allocation above". Fix the contradiction: drop the "does not allocate" claim, or pre-allocate the entry in the load goroutine before taking `mu`.
nit: `loaderFailure.Error()` puts the whole `debug.Stack()` dump in the error string, and every waiter on the flight receives that same error. Callers who log `err` per request will write multi-kilobyte stack dumps N times per panic. Keep the stack as a field (or behind a `%+v`-style accessor) and keep `Error()` to one line with the panic value, which is all test 15 asserts.
