# Adversarial review: plan.md, round 1 (no plan_rebuttal.md existed at review time)
minor: Priority (b) vs (c) is wrong when both are ready (rule 7). In wait(), if f.done and ctx.Done() are both ready, the ctx.Done case only checks closing and then returns ctx.Err(). Go's select picks a ready case at random, so a load that resolved before the waiter ran can still produce ctx.Err(). Rule 7(b) allows ctx.Err() only "while the load is still in flight". Fix: in the ctx.Done branch, after the closing check, do a non-blocking check of f.done and return the load result if it is closed. The plan applies this fix to closing-vs-done but not to ctx-vs-done.
minor: The discard path contradicts itself. The runLoad pseudocode sets f.val = val (the cloned success bytes) even when store is false, but the comment just below says "f.val is nil and f.err is nil on the cancel/close discard path". Today the result is only safe because of an indirect fact: closed/cancel imply closing is already closed, and every waiter checks closing first. Fix: when store is false because of closed or cancel, publish f.val=nil, f.err=ErrClosed. Then a discarded success can never reach a caller, even if wait() changes later.
minor: The private tests are thrown away. The plan says to write the rule 7/8 tests (orphaned-load population, Close joins a blocked Loader, concurrent Close, (bytes,err), capacity with in-flight keys) and then delete them, so the tree matches the public suite. That leaves no regression coverage for the close and orphan paths. These are exactly the behaviours the public suite does not pin, and the easiest to break later. Ship them as blockcache_internal_test.go, deterministic with testing/synctest, and run them under -race.
minor: The LRU structure is not decided ("sentinel head, or nil-empty with explicit mru/lru pointers"). The reason given for a hand-written intrusive list ("avoids any and extra allocations") is weak, because a *entry is allocated per admit anyway. A hand-rolled list is more code to get wrong and maintain than container/list, which is the standard, well-tested choice. Pick one design. If you stay intrusive, use a sentinel ring so there are no nil edge cases, and unit-test unlink and moveToFront at the head, the tail and with one element.
minor: The API block in "Match the spec exactly" drops the doc comments on Cache.Get, Len, Close and New. The exported methods should keep the spec's contract comments (copy semantics, Len lag, Close semantics, panic conditions), or golint/revive will flag them and future maintainers lose the contract.
minor: Calling back into the cache from a Loader is not covered. Close from inside a Loader deadlocks: loads.Wait includes the calling goroutine. Get of the same key from inside its own Loader waits on its own flight and never resolves unless the caller ctx expires. Rule 9 says "must not deadlock". Document these as forbidden on the Loader type, or detect them (for example with a context value marking cache-loader goroutines) and return an error.
minor: A Loader panic is not handled. runLoad has no recover, so a panicking Loader crashes the process from a background goroutine, and no caller stack is involved. Either document that Loader must not panic, or recover in runLoad. If you recover: publish an error to waiters, still delete inflight[key] and close f.done, and keep loads.Done in a defer so Close cannot hang.
nit: Close step 4 (lock after Wait and delete leftover inflight entries) is dead code. runLoad always deletes inflight[key] under mu before close(f.done), so nothing is left after loads.Wait. The step-1 comment "leave inflight in place so finishing loaders can still find their flight" is also wrong, since runLoad holds *flight directly. Remove the step and fix the comment, so readers do not assume an extra invariant.
nit: The flight.ready field has no reader. Waiters always hold *flight and sync through close(done), and the plan's own text admits the "re-lock" path it was meant for does not exist (line 202 "— no: joiners snapshot *flight"). Remove the field.
nit: Close sets entries to empty/nil but leaves the LRU head/tail pointers pointing at the dropped entries ("unlink is unnecessary"). Their byte slices stay reachable for as long as the closed cache is referenced. Reset the list pointers along with the map so "drops all entries" also holds for memory.
nit: Close wakes waiters (closes closing) before loads.Wait, while the spec lists the steps as cancel, wait, wake. This order is allowed by rule 7(a) and is the more responsive choice, but the plan should state the order deliberately in a code comment so nobody "fixes" it to wake after the join.
nit: A Get whose ctx is already Done on a cold key still starts an orphaned load. The spec allows this, since it does not forbid it, and the load populates the cache. Record it as a deliberate choice in a comment or test, because a reviewer may see it as wasted backend load.
nit: The hit path clones e.val while holding mu. Resident values are never mutated after admission, so the copy could happen after unlock to reduce contention on large blocks. If you keep it under the lock, write down the invariant "entry.val and flight.val are immutable and may share a backing array" next to the struct. They do share one in the plan: the same val is stored in both.
nit: The plan text has unfinished thinking in it: line 33's run-on note about nil copies, lines 105-107 pseudocode about nil ctx, line 202's "That happens ... — no:" self-correction, and line 162's stale comment. Clean these up so they do not end up as code comments.
nit: On the discard path, runLoad clones the bytes before it knows whether they will be stored. That copy is wasted when closed or cancelled. It is harmless, but it could check c.ctx.Err() first.
No blocker or major issues remain. The core design is sound: one mutex, Add before go under the same lock that sets closed, a cache-scoped context, flights kept out of entries and Len, discard under mu when closed or cancelled, and only channel and WaitGroup waits, which synctest treats as durably blocking in Go 1.25. It meets every stated rule and passes the public suite as planned. The items above are correctness hardening (the first two minors) and maintainability.
