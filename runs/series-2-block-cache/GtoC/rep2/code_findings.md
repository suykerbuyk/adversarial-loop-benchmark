# Adversarial code review: worktree/blockcache.go, round 1 (no code_rebuttal.md existed at review time)
# Verified independently: go1.27.2 toolchain. `go build`, `go vet` and `gofmt -l` are clean. The public suite passes `go test -race -count=20`. worktree/blockcache_public_test.go is byte-identical to instrument/resolve_public_test.go. I also ran my own -race tests from a scratch copy in /tmp/advbc. Passing: Close joins a ctx-blocked Loader and 3 concurrent Closes all wait for it; every waiter gets ErrClosed; Len()==0 after Close; an orphaned load populates the cache after its only waiter cancels; (bytes, err) returns nil+err and stores nothing; the Loader's slice and the returned slice are both isolated; a 16-goroutine many-key churn with Close mid-run has Len()<=cap throughout. Failing: one priority probe (first finding).
minor: Rule 7 priority (b) vs (c) is not enforced when both are ready. In wait() (lines 173-179), if f.done and ctx.Done() are both ready, Go's select picks a case at random, and the ctx branch returns ctx.Err() without checking f.done. I measured this directly: with the flight resolved first and ctx cancelled afterwards, wait() returned ctx.Err() 974/2000, 981/2000 and 972/2000 times, when rule 7 requires (c) the load result. Through the public API this only happens in a narrow scheduling window (the load resolves, then ctx is cancelled before the waiter goroutine runs), so it cannot be tested deterministically. That is why this is minor and not major. It is still a deviation from "exact semantics", and the plan review had already flagged it. Fix: in the ctx.Done branch, after the closing check, do a non-blocking `select { case <-f.done: return result; default: }`.
minor: The discard path publishes (nil, nil) as a success result. When store is false and err == nil (lines 158-161), runLoad sets f.val=nil and f.err=nil. Waiters never see this today only because of an indirect invariant: c.ctx is cancelled only by Close, which closes `closing` first under the same mutex, and wait() checks `closing` before reading f. If anything else ever cancels c.ctx (for example a future parent context or a per-cache timeout), callers would get ([]byte(nil), nil), a fake successful empty block. Fix: set f.err = ErrClosed on the discard path. The plan review flagged this too, and it was not fixed.
minor: There are no tests of the implementor's own. The worktree ships only the public suite, so the hardest behaviours have no regression coverage. The missing cases are: the rule 7 orphaned-load population, Close joining a blocked Loader, concurrent/idempotent Close during the join, waiters woken with ErrClosed, discarding a result that arrives after cancel, (bytes, err), and per-waiter copies. The public suite exercises none of these. Add a synctest-based blockcache_internal_test.go (my /tmp/advbc/adv_test.go is a starting point).
minor: A Loader panic crashes the process. runLoad has no recover, so the panic happens on a background goroutine, with no caller stack to attribute it to. If a recover is added later, inflight[key] must still be deleted and f.done closed, or waiters hang. Either recover and publish an error to every waiter, as x/sync/singleflight does by propagating, or document on Loader that it must not panic.
minor: Calling back into the cache from a Loader is not handled or documented. Close() from inside a Loader deadlocks forever: loads.Wait includes the calling goroutine, which breaks rule 9's "must not deadlock". Get(sameKey) from inside its own Loader waits on its own flight and returns only when the caller's ctx expires. Document both as forbidden on the Loader type, or detect them, for example with a ctx value that marks loader goroutines.
nit: flight.ready (lines 80 and 165) is written but never read. It is dead state, and it suggests a synchronization protocol that does not exist. Remove it.
nit: The second critical section in Close (lines 129-131), which resets c.inflight after loads.Wait, is dead code. runLoad always deletes inflight[key] under mu before loads.Done, so the map is already empty. Remove it, or replace it with a comment stating the invariant.
nit: Close wakes waiters (close(closing)) before it joins the Loaders, while the spec lists the steps as cancel, wait, wake. Rule 7(a) allows this order, and it is the more responsive one. Add a comment saying it is deliberate, so nobody "fixes" it to wake after the join, which would make waiters block for the length of the join.
nit: runLoad clones the Loader's bytes (line 142) before it knows whether they will be stored. On the close/cancel discard path that copy is wasted. Check c.ctx.Err() first, or clone after the store decision.
nit: The hit path clones e.val while holding c.mu (line 91). For large blocks this serializes every hit on the copy. Resident values are immutable after admission, so the copy could be done after unlock. If you keep it under the lock, document the immutability invariant (entry.val is never mutated) next to the struct.
nit: A Get whose ctx is already Done on a cold key still starts an orphaned load. The spec allows this, and the load populates the cache. Record it as a deliberate choice in a comment.
nit: The hand-rolled intrusive doubly-linked list (mru/lru with nil edges) is correct. I checked unlink at the head, the tail, the only element and the middle, and that evictLRU never runs on an empty list while len>=cap>=1. It is more code to maintain than container/list or a sentinel ring, and nothing tests it directly.
No blocker or major issues remain. Single-flight, copy-on-ingest and copy-on-return, LRU, the Len bound, the Close join and the discard-after-cancel behaviour, the ErrClosed priority, idempotent concurrent Close, and WaitGroup Add-before-Wait ordering (Add happens under mu while !closed) all hold. The implementation passes vet, gofmt, and the race detector, both on the public suite and on my additional adversarial tests.
