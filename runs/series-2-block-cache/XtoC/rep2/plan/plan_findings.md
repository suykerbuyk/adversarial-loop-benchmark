minor: The plan never says how Get checks "the flight has not completed" while holding the lock. The flight struct only has a channel, bytes, and error, with no resolved flag. The plan also leaves open whether the completion channel is closed inside or after the critical section that publishes the result. If it is closed after unlocking, a waiter woken by ctx.Done can see a published result but an open channel. Required fix: add a `resolved bool` set under the mutex, or close the channel inside the same critical section, and make the recheck use that one source of truth. This keeps rule 7's (b)-vs-(c) choice deterministic.
minor: Rule 8 lists the Close steps as cancel, then wait for every Loader to return, then wake waiters with ErrClosed, then drop entries. The plan wakes waiters and clears entries before the join. This matches rule 7(a) and nothing outside the cache can see a difference, because late completions are discarded through the closed and ctx check. The plan should still say the reordering is deliberate and argue why it is safe, so a later maintainer does not "fix" it into a deadlock-prone order such as waking waiters while holding the lock during Wait.
minor: Loader panics are not handled. The Loader runs on a cache-owned goroutine, so a panic kills the whole process. Even if the panic were recovered somewhere, the flight would never resolve and the WaitGroup would never reach zero, so Close would hang forever. The spec is silent on this. The plan should say whether it will recover the panic and turn it into an error published to the waiters, using a deferred publish/Done, or accept the crash on purpose. Either way, publish and Done should sit in a defer so later edits cannot skip them.
minor: The plan does not cover a Get whose ctx is already Done on entry for an absent key. Its design starts a load and then returns ctx.Err(). This is consistent with rule 7, where orphaned loads populate the cache, but it spends a Loader call for a caller that has already left. The plan should state this choice and test it, so it does not look like a bug later.
minor: Re-entrancy is not covered. A Loader that calls Close deadlocks, because Close waits for that same Loader's goroutine. A Loader that calls Get for its own key deadlocks on its own flight until the outer ctx fires. Rule 9 says "must not deadlock", so the plan should document these cases as forbidden Loader behaviour in the Loader or package doc.
nit: Admission handles "key not already resident" but does not say what happens if it is resident. That cannot happen, because a flight only exists while its key is absent and joins are checked after the resident lookup. The plan should state this invariant, or handle the case by replacing the value and promoting the key, so the code does not have an unexplained branch.
nit: Hits and waiter results are cloned while holding the global mutex, so the lock is held for time proportional to the block size. Cache-owned slices are never mutated after admission, so the plan could take the slice reference under the lock and copy after unlocking. If the copy stays under the lock, add a comment explaining the immutability invariant either way.
nit: Add a compile-time interface assertion, `var _ Cache = (*cache)(nil)`. Also state that every error path (ErrClosed, ctx.Err(), Loader error) returns nil bytes. TestErrorNotCached checks `b == nil` on the Loader-error path, and the other two paths should match.
nit: With go 1.25 the plan could use `wg.Go` while holding the mutex instead of separate Add/go/Done calls. That shrinks the chance of an unpaired Done. It could also use testing/synctest, as the public suite does, for its extra close and cancel interleaving tests, rather than ad hoc barriers.
No blocker or major issues remain. I re-checked every rule (1-9) and every public test against the plan and found no stated rule the design would fail. The closed check, flight creation, and WaitGroup Add all happen under one mutex. Admission evicts before it inserts. Loaders run on the cache context in their own goroutines. Completion is discarded after cancellation. Concurrent Close calls share one closeDone.
