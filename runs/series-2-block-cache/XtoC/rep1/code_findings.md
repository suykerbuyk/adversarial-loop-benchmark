# Code review findings: blockcache (XtoC/rep1), round 2

I verified everything myself on go1.27.2. `gofmt -l` is clean, `go vet` is clean, and `go test -race -count=5` passes (public suite plus the implementor's 2 new tests). In a scratch copy I added adversarial tests and ran them under -race (synctest where timing matters). All of them pass:
- An orphaned load still populates the cache, and the Loader gets a live cache ctx even after the caller's ctx is cancelled.
- A Loader returning (bytes, err) has its bytes discarded and Len stays 0.
- The Loader's slice is not retained.
- 5 waiters on one flight each get their own copy.
- A second concurrent Close blocks until the Loader returns.
- A waiter whose ctx fires during the Close join gets ErrClosed.
- Get after Close returns ErrClosed and does not call the Loader.
- 20 rounds of a 32-goroutine stress test (timeouts, errors, evictions, a concurrent Len poller, Close mid-flight): Len never exceeded capacity and was 0 after Close.
The implementor's timing-based test ran 100 times under -race with no flakes. No code_rebuttal.md exists.

The round-1 major is fixed. Close now closes closeCh only after loaders.Wait() (blockcache.go:176-182). runLoad closes f.done when the Loader returns, with f.err=ErrClosed because closed is set, so waiters wake only after their Loader has returned. I confirmed this order under synctest. The round-1 minors are also addressed: empty blocks stay non-nil (cloneBytes), hits copy outside the lock, the nil ctx panic happens before any flight starts, re-entrancy/panic/unbounded-orphan behaviour is documented on Loader, eviction uses `>=`, and the dead ctx.Err() branch is gone.

minor: The 50-waiter result copy still runs under the global mutex. Get does `defer c.mu.Unlock()` (line 111), then `cloneBytes(value)` (line 124), so waiters woken by one flight copy one after another while every other Get, Len and Close is blocked. f.value is immutable once f.done is closed, so read it under the lock and copy after Unlock, as the hit path (lines 89-91) already does.
minor: Test coverage of the subtle rules is still thin. The only new tests are the Close ordering test and the empty-block test. There are no tests for: orphaned load populates (rule 7); ctx.Err() vs ErrClosed priority (7a/7b); the Loader getting the cache ctx, not the caller's; (bytes, err) discarding the bytes (rule 3); the discard-after-cancel path (line 139); Get after Close not calling the Loader; a concurrent second Close blocking on the same join; or per-waiter copies. My scratch tests show all of these behave correctly today, but none are pinned, so a refactor could break them silently.
minor: TestCloseJoinsLoaderBeforeWakingWaiters (blockcache_test.go:34-38) shows "no early wake" with a 20ms wall-clock sleep. On a slow or loaded CI machine an early-wake regression could land after the 20ms window and the test would still pass. The public suite already uses testing/synctest; wrapping this test in synctest.Test plus synctest.Wait() would make the assertion deterministic.
nit: The `case <-c.closeCh:` arm of Get's select (line 107) is now dead code. closeCh is closed only after loaders.Wait(), and every runLoad has already closed its f.done before loaders.Done(). So any waiter (always tied to some flight) is woken by f.done first. I removed the arm in a scratch copy and the full suite plus my adversarial tests still pass under -race. Either delete closeCh (and the isClosed/close logic in Close), or comment that it is a deliberate defensive backstop.
nit: Close-state is still tracked redundantly: `closed`, `c.ctx.Err()` and closeCh. The check `c.closed || c.ctx.Err() != nil` (line 139) now has a comment, but `c.ctx.Err() != nil` can never be true while `closed` is false, because both are set together under mu. One source of truth (plus sync.Once for closeCh if it is kept) would be simpler.
nit: Doc comments are shorter than the spec contract. The Get doc omits single-flight and "each waiter gets its own copy". The Len doc omits "resident-only, may lag by one critical section, never above capacity". The Close doc omits "returns nil" and the "second Close waits for the same join" behaviour. Godoc readers lose the guarantees the implementation actually provides.
nit: The Loader doc warns only against Get on "its own key". A cross-key cycle (Loader(A) does Get(B) while Loader(B) does Get(A)) also deadlocks until Close. The warning should cover any synchronous Get whose load can depend on the calling Loader.
nit: A Get whose ctx is already Done at call time still starts a new flight (and a goroutine plus a Loader call) on a miss before returning ctx.Err(). The spec allows this (orphaned loads populate), but a cheap `ctx.Err()` pre-check before creating a flight would avoid pointless backend load for callers that have already gone. This is a design choice; it should at least be documented.
nit: A waiter whose own ctx fires while Close is joining returns ErrClosed immediately (line 112), i.e. before its Loader has returned. This matches the rule 7 priority, and the waiter was woken by its own ctx, not by Close, so it is not a spec violation. But it is the one path where "Get returned ErrClosed" does not imply "the Loader has returned". A one-line comment would stop a future reader from "fixing" the round-1 ordering incorrectly.

No blocker or major issues remain. Single-flight, LRU/capacity (Len never above capacity under a concurrent poll), copy ownership, error handling including (bytes, err), the rule-7 priority, orphaned-load population, discard-after-cancel, Close ordering (join, then wake), idempotent and concurrent Close, and race-freedom were all verified from source and by tests.
