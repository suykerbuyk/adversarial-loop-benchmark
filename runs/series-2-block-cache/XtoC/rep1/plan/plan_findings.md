minor: Close ordering differs from the spec's literal sequence (rule 8 / Close doc: "cancels..., waits for every in-flight Loader call to return, wakes every current waiter with ErrClosed"). The plan closes the close-notification channel under the mutex BEFORE the wg join, so a waiter can see ErrClosed while its Loader is still running. Rule 7(a) arguably allows this, and since the waiter re-checks `closed` under the mutex, both orders return ErrClosed. But a hidden test of the form "when a waiter sees ErrClosed, the Loader has already returned" would tell them apart. Fix: either wake after wg.Wait (closed is already set under the mutex, so a waiter whose ctx fires in that window still re-checks and returns ErrClosed), or record in the plan/code why waking early is a valid reading.
minor: Rule 3 / public TestErrorNotCached require `b == nil` on error, and the plan never says that waiters on an error outcome return exactly `(nil, err)`. It only says bytes are "not admitted". Make the error result's byte field nil (or skip the copy when err != nil) so no non-nil slice reaches a caller on (bytes, err) or on the ctx.Err()/ErrClosed paths.
minor: The discard path is underspecified. "Loader completion ... discards the result instead of admitting it" must still mark the flight resolved, close its completion channel and delete it from the in-flight map in the same critical section. Otherwise leftover waiters (or later code) depend only on closeCh, and the in-flight map keeps stale entries. Say this explicitly: resolve is unconditional, only admission depends on open/ctx state.
minor: The wg.Done placement is not stated. It should be deferred in the Loader goroutine AFTER the resolve/discard critical section (and resolve should itself be deferred, so a panicking Loader still releases waiters and the join if the panic is ever recovered). Otherwise Close can return while a flight goroutine is still mutating cache state, which weakens "drops all entries" reasoning and hurts maintainability.
minor: Re-entrant Loader behaviour is unaddressed. A Loader that calls c.Close() deadlocks, because Close waits on a wg that includes the caller. A Loader that calls c.Get for its own key waits on itself until Close. Rule 9 says "must not deadlock". Document these as caller misuse in the Loader doc comment, or guard Close (e.g. no self-join), rather than leaving it implicit.
minor: The added test list doesn't assert rule 8's "a Get that has not yet passed the closed check ... does not call the Loader". The public suite checks only errors.Is(ErrClosed), not the Loader call count. Add a call counter to the Get-after-Close test.
minor: No added test checks that the Loader's ctx is cache-scoped rather than the caller's (rule 7). For example, cancel the caller ctx and assert the Loader's ctx.Err()==nil until Close, then assert it is cancelled after Close. The "populates after all waiters cancel" test only checks this indirectly.
nit: The state is redundant: `closed` flag, close-notification channel and cache ctx.Done() all encode the same event, and the flight has both a `resolved` flag and a completion channel. That's three sources of truth to keep in sync over years. Consider using ctx.Done() as the close notification, with `closed` as the only mutex-guarded flag.
nit: The plan copies Loader bytes "immediately after it returns" even when err != nil or the cache is closing. Copy only on the success path to avoid a pointless allocation, and to make the nil-on-error contract obvious.
nit: The invariant "a key is never simultaneously resident and in-flight" (a flight only starts on a resident miss, and resolution removes the flight in the same critical section as admission) is implied but not stated. State it, or make admission defensively replace an existing element, so a later refactor can't double-insert and break Len <= capacity.
nit: Orphaned loads across many distinct keys mean unbounded goroutines and Loader calls. The spec allows this (rule 7), but the doc comment should say so for operators.
nit: The plan should preserve the spec's doc comments on Loader/Cache/New/ErrClosed verbatim in the source (godoc is part of "idiomatic, maintainable Go"), and keep go.mod at go >= 1.25, since the public suite uses testing/synctest.Test.

No blocker or major issues remain: the plan's design (single mutex; flights started and wg.Add done under the same mutex as the closed check; Loader on its own goroutine under a cache-scoped ctx; channel-select waits that are durable under synctest; mutex re-check giving the rule-7 priority; eviction before insert in one critical section; copy on ingest and on every return) satisfies every stated rule and the public suite.
