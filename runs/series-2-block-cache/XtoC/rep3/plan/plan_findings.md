minor: Get step 1 copies resident bytes while holding the one global mutex. Blocks are the unit of a slow backing store and may be large, so every hit then holds up all other hits, every admission and Len for the length of a memcpy. The plan's own immutability rule (published bytes are never mutated in place) makes it race-free to take the slice reference and move to MRU under the lock, then copy after unlocking; an evicted slice stays alive through the local reference. Copy outside the lock, or write down why not.
minor: The new panic/Goexit cleanup path has no planned test. Add a test where the Loader calls runtime.Goexit and check that waiters get the internal error promptly, the flight leaves the in-flight map (a later Get calls the Loader again), and Close returns. Without it, the defer ordering this path depends on can regress unnoticed.
minor: No planned test polls Len concurrently with loads and evictions. Rule 5 says Len is "never above capacity even under a concurrent poll", but the plan only checks Len in sequential access patterns. Add a -race test: many goroutines Get distinct keys on a small-capacity cache while another goroutine keeps asserting Len() <= capacity, and finish with Close and Len()==0.
nit: Recovering a Loader panic and re-raising it is unnecessary. The Loader runs on a cache-owned goroutine, so no caller can recover the panic anyway. Deferred cleanup runs during panicking without recover(). A plain defer plus a `returned` flag (set after the Loader returns) covers both panic and Goexit and keeps the original panic unchanged (no "[recovered, repanicked]" frame). If recover stays, it must be called directly in the deferred func.
nit: The order inside the deferred completion is not pinned down. State that the cleanup locks, admits or discards, publishes, deletes the flight, closes done, unlocks, and only then calls wg.Done(), so that Close returning means every Loader goroutine's flight bookkeeping is finished, not just that the Loader call returned.
nit: The admission check tests both `closed` and "cache-scoped context not canceled". Only Close cancels that context, and it does so under the same lock that sets `closed`, so the two are equivalent. Two sources of truth invite drift. Use `closed` (or ctx.Err()) alone and comment why.
nit: The Loader goroutine is launched after unlocking, so a Close in that gap still lets this already-admitted Get call the Loader with an already-cancelled context. That is allowed (the Get passed the closed check), but issuing the `go` statement while still holding the lock (or skipping the call when ctx.Err()!=nil) closes the window cheaply and makes "no Loader call starts after Close returns" easy to see.
nit: The "otherwise loop/wait again" branch in Get step 4 can never run: each of the three wake events leads to a return. Either remove the loop or comment it as defensive, so a future reader doesn't assume a spurious-wake case exists.
nit: The terminal error used for the Goexit case is unnamed. Give it an unexported sentinel (for example errLoaderAborted) with a doc comment so behaviour and tests can refer to it.
nit: The planned wake of waiters before the join departs from the literal order in the spec ("waits ... wakes every current waiter"). The rebuttal's reasoning holds (Close itself still joins before returning, and rule 7(a) only needs the waiter to get ErrClosed), so put that reasoning in a code comment on Close to stop a future "fix" from moving the wake after wg.Wait.
Summary: all round-1 findings are resolved, including the rule 7 order (closure, then resolved result, then ctx.Err() only while the load is in flight). No blocker or major issue remains.
