major: Rule 7's return priority is closed, then ctx.Err() while the load is still in flight, then the load result. The plan waits only on flight.done, then under the mutex prefers a completed result over the caller's cancellation. Close of done happens in two places: the loader publishes the result and closes done in one critical section, and Close marks closed, closes done, and only then the loader may publish. The second path is fine because closed is already set. The first path is not. A caller whose context is already Done, or becomes Done before the post-wake lock, wakes from the same close and is handed the result even though its context was canceled while the load was still unresolved. That inverts (b) and (c) for every canceled waiter that loses the race to the completion critical section, including a context that was canceled before Get was called. Record an immutable completed flag before closing done, and after wake return ctx.Err() when the caller context is Done and that flag is still false; return the result only when completed is already true. Closed still wins over both.
minor: Successful admission is "if open and the load succeeded, evict LRU if full, then insert." It never says the insert is skipped when this key is already resident. A single-flight map prevents two loads of one key only while a flight is published. Close removes that flight and discards the result, but a loader that returns before cancellation is observed can still be in the publish section, lose the race to closed, get discarded, and leave. A later Get of the same key, after Close has returned and a new cache is not required — within one cache lifetime, after the flight is removed and before this loader's publish lock — can start a second flight, admit the key, and then the late first loader locks, sees the cache still open, and inserts again. The same window exists if publish removes the flight before the insert, which the plan allows ("remove the flight from the map if it is still the matching flight" is unordered relative to insert). A second resident insert of the same key orphans the previous list node or double-links it, so Len and eviction no longer match the map. Under the publish lock, replace an existing resident for that key or skip insert when the key is already resident, and remove the flight only after admission, matching by pointer.
nit: The plan says a later Get re-loads after an error, and that a pending flight does not consume capacity, but it never states that a failed or discarded flight is removed before done is closed. If removal is omitted on the error path, every later Get joins the completed flight and the key never re-loads, which fails rule 3. Remove the matching flight on the error and discard paths in the same critical section that publishes the error and closes done.
