Vibe-Palace · model-adversarial benchmark · Claude · Codex · Grok

When models review each other across vendors, convergence shifts — code quality mostly doesn't

Three Go instruments, each run as a 3×3 of Claude, Codex and Grok playing implementor × adversary, three repeats per cell. On the easy task cross-vendor loops converged more (83% vs 67%); on the hard concurrency task same-vendor did (89% vs 61%) — but every convergence gap here is within noise at three repeats (Fisher's exact p ≥ 0.2) and partly reflects Grok's context-window budget trips. The signals that survive are existence-class, not rates: a converged cross-vendor loop still shipped a live data race (agreement ≠ safety), and on the extensibility task no finished cell built a reusable seam.

01Executive summary

The benchmark asks whether a different-vendor adversarial reviewer raises the quality of a long-lived Go deliverable. Each instrument isolates a different kind of quality — correctness, concurrency-safety, extensibility — under one frozen plan→review→fix loop. The answer is "it depends on what kind of hard," and the three instruments show three different shapes.

The convergence differences are within noise at three repeats; the shipped race and the extensibility floor are the findings that hold.

Discovered extensibility did not emerge — on this task. The loops produced codecs that pass v1 regression and the v2 tests, but by rewriting v1 rather than extending it (best additive-change 0.13; most ~0). 06How it was measured

Isolated, headless cells

Every imp and adv turn is a fresh headless process from a clean directory, with the project's own tooling fully disabled — no plugin skills, no capture hooks, no MCP, and the parent session's identity stripped. A cell communicates only through files. (An early run was discarded when this wasn't airtight.) Runs drove from a systemd user-slice scope so a transport blip couldn't kill them.

Frozen stop rule

Plan loop then code loop, each capped at 3 rounds: the implementor drafts, the adversary tags findings blocker/major/minor/nit, the implementor fixes-or-rebuts, repeat until no blocker/major is open or the cap. The chair records and dispatches only — never breaking a tie. An unresolved blocker/major at the cap is a recorded "did not converge," never a rewrite. Series 3 runs this twice (v1, then the v2 amendment) with the v1 snapshot handed forward.

Grading & tripwires

The chair grades each finished cell identically: build, vet, public tests, a held-out generalization suite the cell never saw; S2 adds -race + a leak gate; S3 adds v1-regression, v1-API-stability, and an advisory additive-change diff. Tripwire: a per-cell cost ceiling ($5, raised to $10 for grok cells); token caps count only fresh work, excluding cache re-reads.

The Grok handicap (reported, not hidden)

grok-4.7's context window is 256K, vs ~1M for the others. On review-heavy tasks it pages its working set through many model calls (hence its cost and some non-convergence/budget trips). Part of S2/S3's cross-vendor gap reflects context size, not review skill — stated as a caveat, not a clean skill comparison.

08Caveats & what's next

Three single runs at three repeats each — coarse error bars. None of the convergence gaps reach significance (Fisher's exact p ≥ 0.2; the easy↔hard "reversal" interaction p = 0.26), so read them as observations, not established effects. The cross-vendor figures are also entangled with Grok's context-window budget trips and (S3) Claude-self cost trips, so "cross-vendor did not settle the hard task within budget" is nearer the mark than "cross-vendor reviewers are worse." The findings we'd stand behind are existence-class, not rate-class: a converged loop can ship a race, and no finished cell discovered a seam. The additive-ratio metric is advisory and gameable, but its uniform near-zero across finished S3 cells is a robust directional signal.

Next: more repeats for significance; a cost/latency-normalized reviewer comparison that removes the Grok window handicap; and, given S3, a task that explicitly rewards extensibility to see whether prompted extensibility closes the gap discovered extensibility left wide open.

09Appendix — the three tasks and what they measure

Each series is a frozen Go instrument chosen to isolate one kind of quality. All share the public spec + public tests shipped into the cell; a held-out suite (never shown to the cell) grades generalization. Held-out cases are withheld here to keep the instruments re-runnable.

Series 1 — layered configuration resolver

Task. A Go config package that computes an effective configuration from four ordered layers (defaults, file, env, flags); a higher layer overrides a lower one, with a validated effective LogLevel.

Intended to measure — baseline correctness. One subtle trap: a present zero value (false, 0, "") must override a lower layer, which the common "merge non-zero fields" shortcut gets wrong. It's a small, pure, long-lived deliverable — the question was whether the models solve it at all and whether a cross-vendor reviewer improves it. Outcome: all solved it (saturated), so it couldn't grade quality — only how the loop converged.

Series 2 — bounded concurrent single-flight block cache

Task. A thread-safe cache in front of a slow backing store: concurrent misses for one key must coalesce to a single load (single-flight); capacity-bounded with LRU eviction; Close cancels in-flight loads and leaves no goroutine.

Intended to measure — concurrency & resource correctness. The daily hazard surface of storage and systems code: data races, duplicate work under contention, goroutine/resource leaks, lifecycle at shutdown. Graded under the race detector with a leak gate, so there are real, hard-to-see defects for the adversary to catch — the test of whether adversarial review actually raises safety on concurrent code. Outcome: it discriminated; cross-vendor and same-vendor convergence differed (within noise); and, decisively, one converged loop still shipped a race.

Series 3 — versioned write-ahead-log record codec (two-phase)

Task. Phase 1: encode/decode framed WAL records (Put/Delete) with a length prefix, type tag and CRC. Phase 2 (revealed only after v1 converges): add a nested, variable-length Batch record and a format version, while keeping every v1 stream decodable and the v1 API intact.

Intended to measure — discovered extensibility (architectural soundness over time). The real question for long-lived code: does the loop produce a design that absorbs a requirement added after the fact, without tearing up what exists? The "design for extension" hint was deliberately removed so the seam had to be the models' own idea; the additive-change score measures how much of v2 was new code vs edits to v1. Outcome: no finished cell built the seam on this task — discovered extensibility did not emerge here.
